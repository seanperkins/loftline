# Decisions log (append-only)

- **scaffold** — Toolpath moves are in machine coordinates; `MachineCoordinates` (CAMCore) is the
  single material→machine mapping for XY origin and Z-zero mode. Generators think in depth
  below the material top.
- **scaffold** — Document geometry uses a fixed material frame (lower-left = 0,0). The XY origin
  choice only affects G-code, so moving the origin never moves the design.
- **scaffold** — Safe Z and home Z are stored as heights above the material top (VCarve style);
  `home` XY is in machine coordinates.
- **scaffold** — Arcs in `Move` carry an absolute machine-XY centre; the post converts to
  incremental IJ (Mach4 default) or linearises.
- **scaffold** — Drilling is emitted as explicit G0/G1 pecks (no G81/G83) for portability.
- **scaffold** — CGeom exposes a C API (not C++ interop) so Swift targets build without
  `-cxx-interoperability-mode`. Boost dependency trimmed to the Voronoi headers +
  `boost/cstdint.hpp` + Boost.Config.
- **scaffold** — Voronoi input is snapped to an integer grid (`scale`, default 10000/unit);
  edges come back pre-sampled with inscribed radius so V-carve does not need parabola math.
- **scaffold** — Seeded tool library uses fixed UUIDs (`00000000-0000-4000-8000-00000000000N`)
  so documents referencing seeded tools stay valid.
- **scaffold** — Generic GRBL profile uses `M0` (pause) for tool changes since GRBL 1.1 has no M6.
- **scaffold** — Validator checks the toolpath XY *extent* against travel (the job origin's
  position on the bed is unknown to Kerf).
- **scaffold** — Swift targets use Swift 5 language mode under tools-version 6.0 to avoid
  strict-concurrency friction; public model types are still `Sendable`.
- **post** — Coordinates use fixed `decimals` (4 inch / 3 mm), feeds `feedDecimals`; numbers are
  formatted with the POSIX locale and "-0.0000" is normalised to "0.0000".
- **post** — Modal output: repeated G0/G1 words, unchanged axes and unchanged F are suppressed.
  Arcs always state G2/G3 plus X and Y (Mach4 full circles need them). Any non-motion line
  (spindle, dwell, tool change) makes the next motion restate its G-word; after a tool change
  position and feed are forgotten, so the first cut always restates F.
- **post** — Safety net in the writer: an XY rapid starting below safe Z first emits `G0 Z<safe>`;
  a rapid whose target is below safe Z is split into XY at safe Z then a Z-only rapid.
- **post** — Tool change sequence: retract to safe Z, profile `toolChange` lines (also for the
  first tool, so GRBL pauses with M0 to load it), optional `G43 H<n>`, `G0 Z<safe>`, spindle
  on, `G4 P<seconds>` (seconds — Mach4/GRBL default). Spindle is restarted (with dwell) when the
  RPM changes within the same tool. Spindle speed outside the profile's RPM range throws.
- **post** — `post` emits toolpaths in the given order; `postCombined` groups by tool
  (`ToolpathOrdering.groupedByTool`) first. A tool change happens when the tool *id* changes.
- **post** — Comments are forced to ASCII (° → " deg", diacritics stripped) and template
  values substituted into comments have parentheses turned into brackets.
- **post** — Helical arcs are emitted as G2/G3 with Z when `helicalArcs`; otherwise (or with
  `arcOutput = .linearize`) arcs are linearised to `arcTolerance`.
- **post** — Header time estimate (`PostTimeEstimator`, public) = feed length/feed + rapid
  length/`rapidRate` + dwells + spindle dwell per spindle start; no acceleration model. Kept in
  PostCore so the post does not depend on the preview workstream's estimator.
- **post** — Golden programs are inline raw-string literals in `PostGoldenTests.swift` (no test
  resources, so Package.swift stays untouched).
- **post** — GCodeValidator rules (shared by toolpath and G-code checks via `MotionChecker`):
  error = travel span > machine travel (arcs sampled via I/J), Z below material bottom minus
  `limits.maxSpoilboardCut` (both Z-zero modes), XY rapid with Z below the material top, feed
  move below the material top with the spindle off, feed move without F or with F <= 0, S
  outside min/max RPM, arc start/end radius mismatch, arc without I/J/R. Warnings = XY rapid
  below safe Z but above the material, rapid plunge below the top, XY rapid before Z is known,
  feed above `maxFeed`, G91, units differing from the profile, no G20/G21, no M30/M2,
  unparseable text. Repeats of the same rule are collapsed into one issue "(N more)". G-code
  is checked in the units it declares (G20/G21), defaulting to the profile's.
- **cad-io** — SVG import places the SVG page's lower-left corner at document (0,0) and flips Y.
  User units without a physical size are CSS px (96/in); `preserveAspectRatio` (meet/slice/none)
  is honoured. Top-level `<g>` elements (and Inkscape layers) become layers; loose top-level
  elements go to an "SVG Import" layer. `<text>`/`<image>` are skipped with a warning.
- **cad-io** — Circular SVG arcs stay `.arc` segments (split at 180°); elliptical/rotated arcs
  become cubics. Quadratics become cubics everywhere (SVG, CoreText, EPS).
- **cad-io** — SVG export page spans `min(0, bounds.min)…bounds.max` with physical width/height
  in document units, so designs in the material frame round-trip exactly.
- **cad-io** — DXF without `$INSUNITS` falls back to `$MEASUREMENT`; with neither, values are read
  as document units and a warning is returned. Loose open entities on the same layer are joined
  (0.0005 in / 0.01 mm) so imported outlines are usable as closed vectors.
- **cad-io** — DXF SPLINEs with control points are evaluated (rational de Boor) and sampled to a
  polyline; fit-point-only splines become Catmull-Rom cubics. Block INSERTs are expanded
  (layer-0 entities inherit the insert's layer); MINSERT arrays, TEXT, HATCH, DIMENSION are skipped
  with a warning. OCS extrusion Z=-1 mirrors X.
- **cad-io** — DXF export is R12 ASCII: one POLYLINE with bulges per path (cubics flattened at
  0.0005 in / 0.01 mm), full circles as CIRCLE, layer table with nearest basic ACI colour.
- **cad-io** — Text size is the CAP HEIGHT in document units (what is measured on the finished
  sign); the CoreText point size is derived from the font's cap height. Unknown fonts throw
  `TextOutliner.TextError.fontNotFound` instead of silently substituting. Glyph contours are
  normalised (outer CCW, holes CW) by nesting depth; overlapping contours (some variable fonts)
  are not unioned.
- **cad-io** — `.kerf` versioning lives in `KerfFile` (CADCore): JSON-level migrations keyed by
  the version they upgrade from, newer files rejected, missing `formatVersion` = 1.
  `DocumentFile` writes `{formatVersion, document, operations: [], tools: []}` so a design-only
  file opens as a `KerfProject`. `KerfFile.currentVersion` must track
  `KerfProject.currentFormatVersion`; the app should decode projects via
  `KerfFile.decode(KerfProject.self, from:)` to get migrations.
- **cad-io** — Test fixtures live in `Tests/Fixtures/CADCore/` (outside any target, loaded via
  `#filePath`) so no `Package.swift` resource change was needed.
- **cad-io** — EPS import is a minimal path interpreter (no PostScript programming); PDF-based
  `.ai` files are rejected with a "save as SVG" message.
- **cam-2d** — Generators build `[CutPoint]` (material XY + depth) and emit through
  `Ops2D/Support/ToolpathBuilder`, the only place that turns them into `Move`s (via
  `MachineCoordinates`); it retracts to safe Z before every XY rapid and ends at safe Z.
- **cam-2d** — Arcs: toolpaths are computed as polylines (Clipper round-join offsets at the
  document tolerance), then `ArcFitter` re-fits G2/G3 arcs (≤180°, ≥3 chords, within 2× tolerance)
  on constant-depth runs. Ramps and tabs stay linear. `ProfileParameters.preferArcs = false` turns
  fitting off for profiles.
- **cam-2d** — Profiles use the even-odd region of ALL selected closed vectors, so nested vectors
  become islands: "outside" on a frame cuts outside the outer edge and inside the hole. Open
  vectors are always cut on the line, alternating direction each pass with no retract.
- **cam-2d** — Climb (clockwise spindle) keeps the finished part on the right of travel. So outside
  profiles run CW, while inside profiles and pocket walls run CCW and pocket islands run CW. Closed
  vectors cut "on" behave like outside.
- **cam-2d** — Tabs:
  - The raised length along the toolpath is tab length + tool diameter, so the bridge left in the
    part equals the tab length.
  - Added an additive `TabSettings.spacing: Double?`. When set, it overrides the count.
  - Triangular tabs peak at the tab top in the middle.
- **cam-2d** — Ramps:
  - Smooth: linear descent over max(length, Δ/tan(maxAngle)), then the ramp section is re-cut.
  - Zigzag: an even number of back-and-forth legs within `length`.
  - Spiral: one helical lap per pass plus a final flat lap.
  - Open chains always use zigzag. When a lead-in is enabled the ramp is skipped, because the
    plunge happens in the waste at the lead start.
- **cam-2d** — Plunges rapid down to a gap (0.05"/1 mm, never more than safe Z) above material
  known to be cleared (the top, or the previous pass depth), then feed at the plunge rate.
- **cam-2d** — Pocket offset clearing:
  - Each component is cut inside-out. A ring waits only for the deeper rings adjacent to it.
  - Rings and raster lines are linked at depth when a straight move, or a walk along the
    tool-centre boundary, stays inside the tool-centre region and is ≤ 2× the tool diameter.
    Otherwise the tool retracts.
  - Stepover is clamped to 95% of the diameter.
- **cam-2d** — Clearance tool:
  - The larger tool clears the whole pocket.
  - The primary tool then cuts the wall contour, plus offset-ring fragments near the rest material
    (the pocket minus the big tool's morphological opening).
  - The clearance tool is ignored unless it is larger than the primary tool.
- **cam-2d** — Drilling:
  - One hole per closed path, or per point-like path, de-duplicated. Arc-only paths use their
    exact centre; others use the bounds centre.
  - Pecks are explicit G0/G1 moves. Between pecks the tool retracts to `retractHeight` (capped at
    safe Z), then rapids back to 0.02"/0.5 mm above the previous peck.
- **cam-2d** — `ToolpathStats` (Ops2D/Support) computes cut and rapid length and an estimated time:
  Σ length/feed + rapids/rapidRate + dwells + an allowance per tool change. The preview's
  `MachiningTimeEstimator` can delegate to it.
- **cam-2d** — Fluting and Texture are implemented too (same folder):
  - Fluting ramps over `rampFraction` of the length (cosine when smooth). Symmetric flutes
    alternate direction.
  - Texture uses a seeded SplitMix64 to place sine-shaped dips along lines at `angle`, retracting
    between strokes.
- **cam-vcarve** — Selected closed vectors are merged with the even-odd rule (Clipper union,
  snapped to the Voronoi grid: 1e-4 in / 1e-3 mm), so nested contours are holes (text
  counters). Open vectors are ignored with a toolpath warning.
- **cam-vcarve** — Depth = startDepth + min(max(0, r − tipRadius) / tan(angle/2), limit), where
  limit = min(flatDepth, bit's full cutting depth). `flatDepth` is measured below `startDepth`.
  When the bit itself limits depth (no flat depth set), the toolpath carries a warning and the
  flat area is cleared like a flat-depth carve.
- **cam-vcarve** — Flat area = region inset by tipRadius + limit·tan(angle/2). With a clearance
  tool it is pocketed (offset or raster, stepped by the clearance tool's stepdown) and the V-bit
  traces the flat area's boundary at the flat depth plus the clamped medial axis (corner
  cleanup). Without one the V-bit clears it with offset/raster passes at its own stepover.
  Toolpath order: clearance tool first, then V-bit.
- **cam-vcarve** — `VCarveParameters.passDepth == nil` means a single pass (per the model doc);
  with a value, pass k only re-cuts where the target depth exceeds level k−1.
- **cam-vcarve** — Plunges go from safe Z at the plunge rate; medial-axis chains are walked
  through junctions to minimise lifts, gaps ≤ 0.002 in (0.05 mm) are linked at depth.
- **cam-vcarve** — Inlay: female = V-carve flat at `pocketDepth` P. Male = V-carve of
  (mirrored vectors' bounds grown by `maleBoundaryMargin`) minus the mirrored vectors, start
  depth S, total depth P (male flat depth below start = P − S). Walls coincide when the plug top
  sits S below the female surface, so the bottom gap is P − S; `glueGap` is enforced as the
  minimum bottom gap (S + glueGap ≤ P, else invalidParameter). Gaps are reported in toolpath
  metadata (`bottomGap`, `boardGap`). The male is generated in place (mirrored about its own
  bounds centre) — cut it on a separate board; `part: .both` emits female then male toolpaths.
- **cam-3d** — STL files have no units; `STLImporter` assumes millimetres (`sourceUnits`, default
  `.millimeter`) and converts to the document units. Vertices are merged on a 1e-7 grid and
  degenerate triangles dropped. A file whose size matches the binary layout is binary even if
  its header starts with "solid".
- **cam-3d** — `PlacedModel` mapping: material XY = mesh XY × `scale` + `offset`; mesh Z is
  stretched so its top sits `zTop` and its bottom `depth` below the material top. Outside the
  model's triangles the relief surface is that bottom plane. `ModelPlacement.place` fits/centres
  a mesh on the job.
- **cam-3d** — The relief heightmap is *conservative*: each cell stores the shallowest mesh point
  anywhere in its square (triangle clipped to the cell), and the drop-cutter honours each cell
  at its point nearest the tool axis. Finishing therefore never gouges the mesh at any
  resolution; the cost is up to ~slope × cell size of extra stock, so finer resolution = closer
  finish. Grids are capped (30M cells) and auto-coarsened with a toolpath `warning`.
- **cam-3d** — Roughing = z-levels (`passDepth` ?? tool stepdown, evenly spaced) raster-cleared
  where a flat cutter of radius R+allowance, raised by allowance, clears the model (allowance
  left both sideways and vertically). Levels are nested, so rapid descents stop 0.04 in / 1 mm
  above the previous level. `PocketStrategy.offset` is cut as raster (angle 0) for now and
  `profilePass` is ignored; noted in toolpath metadata. Roughing requires an end mill.
- **cam-3d** — Relief tool centre stays inside the boundary vectors (or the model footprint);
  output order is roughing then finishing, one toolpath each.
- **cam-3d** — Fluting/Texture generators live in `Ops3D/FluteToolpathGenerator.swift` and
  `Ops3D/TextureToolpathGenerator.swift` (public) because `Ops2D/` is owned by cam-2d. If cam-2d
  has not implemented `FlutingOperation`/`TextureOperation`, the integrator can forward their
  `generate` to these. Flute passes alternate direction (no retract between passes); texture
  strokes are half-sine scoops from a SplitMix64 PRNG seeded by `seed`, linked by feeding
  0.04 in / 1 mm above the top when close, region = selected closed vectors or the material.
- **preview** — Simulation sweeps each flattened motion segment analytically: every cell near
  the segment is cut by the tool profile (flat/ball/V) centred at the closest XY point of the
  segment. Segments are split so each piece descends ≤ one cell, which keeps ramps and helices
  accurate. Cuts are clamped to the material thickness, so spoilboard cuts are not shown.
- **preview** — Drill tools with an `angle` are simulated as a V point; without one, they are
  simulated as flat. Engraving tools are simulated as a V with a flat tip.
- **preview** — `MachiningTimeEstimator.estimate` gained a defaulted `toolChangeSeconds`
  parameter (default 90 s per manual change). Arcs are timed by their true helical length.
  There is no acceleration model.
- **preview** — The 3D preview uses SceneKit. The heightfield becomes a vertex-coloured mesh,
  decimated to ≤ 200k vertices. The cell size is automatic (~800k cells, min 0.004 in /
  0.1 mm). Scrubbing backwards restores the nearest checkpoint (every ~1/12 of the steps)
  and replays from there. The preview opens on the finished result.
- **preview** — App shell integration point: `ToolpathPreviewPanel(document:toolpaths:postProfile:)`
  provides the 2D/3D tabs. The canvas overlay uses
  `ToolpathOverlayRenderer.draw(ToolpathOverlay(toolpaths:coords:), in:transform:)`.
  `PreviewSamples.demo()` provides demo toolpaths.
- **app-shell** — Added test target `KerfAppTests` (depends on the `KerfApp` executable via
  `@testable import`) in Package.swift — additive only. App view-model logic lives in
  `Sources/KerfApp/Model/` as pure Swift so it can be tested without UI.
- **app-shell** — Documents use SwiftUI `DocumentGroup` + `ReferenceFileDocument` (`KerfDocument`).
  Undo is snapshot-based: every edit goes through `KerfDocument.perform`, which registers the
  previous `KerfProject` with the window's undo manager (also drives the dirty flag). The UTI
  `com.seanperkins.kerf.project` is declared in Info.plist by `scripts/bundle.sh`.
- **app-shell** — Toolpath results are kept in memory only (not saved) and marked stale when the
  operation, the design or the tool library changes; export recalculates stale toolpaths
  synchronously first so the G-code always matches the parameters.
- **app-shell** — Toolpath parameter edits happen on a draft in the inspector and commit on
  Save/Calculate (one undo step per commit, not per keystroke).
- **app-shell** — Combined G-code export groups toolpaths by tool by default (toggle in the export
  sheet). The validator runs on both toolpaths and generated text; errors require "Save Anyway".
- **app-shell** — Changing document units in Job Setup converts geometry, job, grid and all
  operation lengths (angles/percentages untouched). New operations get inch defaults ×25.4 in mm
  documents; profile cut depth defaults to the material thickness.
- **app-shell** — User post profiles are loaded from `~/Library/Application Support/Kerf/posts/*.json`
  (same id overrides a built-in). Default post follows document units (Avid inch/mm).
- **app-shell** — The canvas draws a basic 2D toolpath overlay (cuts solid per-operation colour,

## drawing

- **drawing** — Pure editing model lives in `CADCore/Editing` (PathNodes, ShapeNodes, TransformHandles,
  SnapEngine, PenPath, Grouping) and is unit-tested; the canvas only maps gestures onto it.
- **drawing** — Node editing works on an "editable form" of each path: arcs become cubic Béziers and
  closed paths get an explicit closing segment, so node indices are stable. The first node edit
  therefore converts that shape's arcs to cubics and drops parametric provenance (rectangle,
  circle…) — the shape becomes a plain drawn vector.
- **drawing** — Deleting a node between two curves keeps the outer handles (approximate merge);
  otherwise the neighbours are joined with a line. Paths never drop below 2 nodes (open) / 3 (closed).
- **drawing** — Groups are a `groupID` on `Shape` (optional, so older .kerf files still decode; no
  format-version bump). Clicking any member selects the group; grouping a member absorbs its whole
  group (flat groups, no nesting). The old merge-into-one-shape action is now "Combine", and
  "Break Apart" splits multi-path shapes.
- **drawing** — Snapping: object points (nodes, segment midpoints, bounding-box centres) within
  8 screen points win over the grid; Command temporarily disables snapping. Moves snap a corner,
  centre or node of the selection onto targets. Snap-to-grid moved to ⌘' (⇧⌘G is now Ungroup).
- **drawing** — Transform handles: corner/edge handles scale about the opposite handle (Shift keeps
  proportions, Option scales about the centre); the round handle above the box rotates (Shift
  snaps to 15°). Mirroring stays on menu/inspector buttons.
- **drawing** — Bézier pen is a separate tool (P); the old click-through smooth curve remains as
  "Smooth Curve". Canvas single-key tool shortcuts: V N R C E L P T.

## advanced-ui

- **advanced-ui** — Manual profile tabs are `TabSettings.manualTabs: [TabAnchor]?` (optional, so older .kerf files decode unchanged). An anchor is (shape id, path index, fraction of the flattened path length), so tabs follow the vector when it moves, scales or rotates. When manual, each anchor goes to the toolpath loop nearest its position; loops with no anchor get no tabs; overlapping tabs on a loop are merged (first one kept). (Anchor placement superseded by tab-warnings, 2026-10-22, issue #9: an anchor attaches only where its own vector's stretch is cut, and is reported otherwise.) nil = the existing automatic layout.
- **advanced-ui** — Tab editor: "Edit on Canvas" in the Profile inspector (Tabs → Placement: Manual). Click one of the toolpath's vectors to add a tab, drag a tab to slide it along the vectors, option-click to delete, Esc/Done to finish. Each edit is one undo step. Switching to Manual seeds evenly spaced anchors (tabs-per-vector on each closed path).
- **advanced-ui** — New Toolpath → Inlay opens a wizard that creates TWO InlayOperations (part = female "Pocket", part = male "Plug") sharing one set of settings, so each board's program can be saved separately. The single-operation `.both` part is still supported in the inspector.
- **advanced-ui** — Importing an STL no longer places the model silently: it opens "Place 3D Model" (size with locked aspect, centre/lower-left/custom position, model Z height, Z offset below the top) and by default creates two Relief3D toolpaths: "<name> Roughing" (end mill, finishing off) and "<name> Finishing" (ball nose, roughing off). Models can be re-placed later from the model's context menu. Multiple STLs queue their dialogs; import warnings are shown after the last one. `ImportService.importFile` still places STLs directly for headless use.
- **advanced-ui** — "Save All Toolpaths" offers: one file grouped by tool (default), one file in list order, one file per toolpath, one file per tool. Multi-file modes ask for a folder; clashing names get `_2`, `_3` suffixes. Every file is validated; saving with errors asks for confirmation.
- **advanced-ui** — "Check Toolpaths…" (⇧⌘K) validates each enabled toolpath on its own plus the combined program, showing only combined-program issues not already listed per toolpath. Uncalculated and failed toolpaths are listed as warnings.
- **advanced-ui** — The Toolpaths sidebar shows each toolpath's tools and estimated time, plus a footer with total time and the tool load/change sequence (grouped by tool or list order). The total sums per-toolpath estimates (no tool-change allowance).
- **advanced-ui** — Pocket's primary tool is labelled "Finish tool"; the clearance tool is only used when it is larger than the finish tool, and the form says so. Drill has a "Peck drilling" toggle (off = peck depth 0, single plunge) and a per-hole peck summary. `DrillOperation.peckDepths` is now public for that summary.
- **advanced-ui** — Tab spacing is now scaled with the other tab lengths when converting a document between inch and mm.

## review-fixes (ordering, inlay, open vectors, relief, booleans, async calc)

- **review-fixes** — "Group by tool" is now OFF by default and is one shared setting (`kerf.groupByTool` in UserDefaults) read by Export G-code, Check Toolpaths, the tool-change summary and the 3D preview, so the simulated order always matches the exported order. Save All defaults to "One file, in toolpath order". When grouping is on, `ToolpathOrdering.groupedByTool` only pulls a toolpath forward into an earlier same-tool group if it is not a profile, does not jump an earlier pass of its own operation, and its XY footprint (padded by both tool radii) does not overlap any toolpath it jumps. Otherwise the user's order wins.
- **review-fixes** — The inlay wizard creates the plug (male) operation disabled; the validator reports an error when inlay female and male toolpaths are in one program (the plug is generated in place over the pocket).
- **review-fixes** — SVG import closes subpaths whose ends meet within 0.0005 in / 0.01 mm (same as the DXF join tolerance; DXF already closed such loops through `joinOpenPaths`). Profile adds a metadata warning when Outside/Inside is selected but open vectors were cut on the line.
- **review-fixes** — New 3D Relief toolpaths rough with the first end mill in the library when the primary tool is not an end mill (roughing is turned off if the library has none). The roughing tool picker only lists end mills.
- **review-fixes** — Each `[Path]` argument to PathOps union(a,b)/subtract/intersect/xor/offset is one shape read even-odd (the CAM rule), normalised with an even-odd union first, so same-direction holes survive. Weld uses `union(shapes:)` (each shape normalised separately, then non-zero union); Subtract unions the cutters first. The single-list `union(_:)` keeps "every path is its own region" semantics.
- **review-fixes** — Export / Save All / Check sheets recalculate stale toolpaths in the background (`KerfDocument.calculateAndWait`) with a progress row and Stop button, and post only once results arrive. Every calculation gets a monotonic generation stamp; a result is stored only if newer than the stored one. A Calculate request for an operation that is already calculating is queued and runs once the current one finishes.

- **review-fixes** — **Profile leads are validated against the waste side.** The configured lead is tried first, then straight approaches (diagonal back, diagonal forward, pure normal) at shrinking lengths; the first that keeps every point in the tool-centre waste region wins, otherwise no lead. Fixes inside profiles starting at a sharp corner backing through the wall.
- **review-fixes** — **Pocket reports unreachable regions** as `metadata["warning"] = "N region(s) too small for the tool"` (computed with the finish tool, so it also covers rest clearing).
- **review-fixes** — **"One file per tool" follows the grouped-export safety rules.** Files are the runs of `ToolpathOrdering.toolGroups` (profiles never move, overlapping toolpaths keep their order), so a tool may get several files; names carry a run-order prefix (`01_`, `02_`, …).
- **review-fixes** — **The toolpath editor writes through.** Every form change is committed immediately (`updateOperationLive`), merged into one "Edit Toolpath" undo step until another change, undo or save. The Save button is gone; Revert restores the operation as it was when selected.

## vcarve-parity (round 1)

- **vcarve-parity** — Multiple flat-area clearance tools: `flatClearanceToolID` stays the first
  tool and `extraClearanceTools: [VCarveClearanceTool]` (V-carve and inlay) adds more, run in
  list order like Vectric's clearance tool list (the UI says to list them largest first; the
  order is not re-sorted). Tool k only cuts where the flat area minus everything earlier tools
  swept (their centre region grown by their floor radius) is non-empty: its centre region is
  (flat area inset by its wall clearance) ∩ (rest grown by its floor radius), cleared with
  rings/raster at its own stepdown. A later tool with nothing left is dropped with a warning.
  Tapered engraving tools may be clearance tools: their wall clearance is tip radius + flat
  depth · max(0, tan(tool half-angle) − tan(V half-angle)), capped at the tool radius.
  New parameter fields are decoded with `decodeIfPresent`, so older `.kerf` files open unchanged.
- **vcarve-parity** — Corner sharpening is a per-tool flag on the extra clearance tools
  (`VCarveClearanceTool.cornerSharpen`, shown only for tools with an angle), as in Vectric where it
  applies to second-or-later engraving tools. After its flat-depth clearing, the tool follows the
  region's medial axis wherever it lies in the flat area but outside everything already swept,
  at depth start + min(flat, (R − tip radius) / max(tan tool half-angle, tan V half-angle)), so the
  cone never cuts the V walls. The V-bit still traces the flat boundary and full medial axis
  afterwards, as before.
- **vcarve-parity** — Inlay plug boundary: `InlayParameters.plugBoundary` = `.boundaryOffset`
  (the old behaviour: bounds grown by `maleBoundaryMargin`), `.vectorOffset` (outer loops of the
  mirrored vectors grown by the margin, so counters are still cleared) or `.sheetLimits` (the
  whole material rectangle; slow without a clearance tool on a big sheet, like any huge flat
  area). `surfaceClearance` (nil = P − S, the old value) is the plug carve's depth below its
  start depth, i.e. how far the plug board's cleared floor sits above the pocket board when
  seated; it is reported as `boardGap`, must be > 0 and, when set, less than the material
  thickness. The bottom (glue) gap stays P − S.
- **vcarve-parity** — V-bit engraving of open vectors lives in the V-Carve toolpath:
  `VCarveParameters.openVectorDepth` (nil = ignore open vectors with a warning, as before) engraves
  each selected open vector along the line at start depth + depth; `openVectorTaper` (0…0.5) eases
  each end from the surface over that share of the length with a cosine profile (sketch-style
  strokes that start and end as points). The strokes join the V-bit's carve strokes, so pass
  depth, ordering and the move writer apply. A selection of only open vectors is valid when
  engraving is on. Closed vectors are still V-carved, never engraved along their outline.
- **vcarve-parity** — V-Carve `useSelectionOrder` / `useVectorStartPoints` (Vectric's "Use
  Vector Selection Order" / "Use Vector Start Points"). Strokes are assigned to the first selected
  shape (selection order = `setup.shapeIDs`, which the app fills in click order) that contains
  their middle point, or whose open path they lie on. Selection order cuts each shape's strokes
  together, per pass, shapes in order; strokes in no shape go last. Start points rotate closed
  loops (flat-area outlines, clearance rings) to begin at the vertex nearest the shape's first
  path start, start each shape's walk there, and keep engraved open vectors in their drawn
  direction. Medial-axis chains are not re-split at start points. Inlay does not offer these
  options (its plug geometry is mirrored).
- **vcarve-parity** — PhotoVCarve is a new operation kind `.photoVCarve` (`PhotoVCarveOperation`,
  additive enum cases in `OperationKind`/`AnyOperation` and their app switches). The picture is
  loaded with ImageIO, downsampled to ≤ 800 px on the long side, converted to 8-bit grey and
  stored in the operation (`GrayImage`, base64 in the `.kerf` JSON) so the file is
  self-contained. Grooves are parallel lines at `angle`, `lineSpacing` apart, across a
  placement rectangle (origin + width, height from the aspect); along each line the groove's
  top width = darkness × spacing, i.e. depth = max(0, w/2 − tip radius) / tan(half-angle), capped
  by the bit; samples shallower than `minDepth` lift the bit. Lines alternate direction. No
  bitmap is drawn on the canvas yet; the toolpath overlay shows the placement. New Photo
  V-Carve toolpaths start centred at 80% of the material.
## cam-3d parity round 1

- **cam-3d** — **3D roughing offset strategy and profile pass (3d-roughing).** Each Z level's tool-centre
  region is now contoured (marching squares) from a grid of flat-cutter drop depths computed for
  the whole heightmap at once (`ReliefHeightmap.eroded`, row-wise sliding minima). The cutter is
  grown by allowance + 1.5 cells so the contour is safe between grid points; saddle cells are
  always split; contours are simplified within tolerance/2 and shrunk by the same amount, then
  clipped to the boundary. The region is cleared with the 2D `PocketPlanner` (radius 0):
  `.offset` = contour-parallel inside-out rings, `.raster` = zig-zag lines plus the region contour
  when `profilePass` is on. Links stay inside the level's region (`RegionLinker`), other moves
  retract. This replaces the earlier per-raster-line sampling, so raster roughing toolpaths changed.
- **cam-3d** — **Composite models (3d-multiple-models).** `Relief3DParameters.additionalModelIDs`
  (optional, so older files decode) lists models machined together with `modelID`. They are
  rasterised into one heightmap where each cell keeps the shallowest point of any model (a union);
  cells no model covers sit at the deepest model's bottom plane. The default area is the union of
  the models' footprints. Missing combined models are skipped with a toolpath warning (a missing
  primary model is still an error). The inspector lists the other models under "Combine with".
- **cam-3d** — **Offset and spiral 3D finishing (3d-finish-offset).** `FinishingSettings.strategy`
  (optional; nil = raster). Offset = the boundary region's inward rings (`PocketPlanner.offsetLevels`,
  radius 0) cut outermost first, each started at the point nearest the tool and linked along the
  surface when the next ring is within 2.5 × stepover. Spiral = each run of levels with exactly one
  ring is blended into one path (going once round ring k while moving linearly onto ring k+1,
  matched by arc-length fraction), ending with a full lap of the innermost ring; where the area
  splits into several rings those levels are cut as offset rings. Every point is dropped with the
  drop-cutter, so no pattern can gouge the model; on very non-convex boundaries a blended spiral
  point may stray slightly outside the boundary between two rings.
- **cam-3d** — **3D rest machining (3d-rest-machining).** `FinishingSettings.restToolID` names the
  larger tool that already finished the surface ("Rest after" in the inspector). On the heightmap
  grid (drop-cutter rule: each cell square reached at its point nearest the tool axis) Kerf drops
  the larger tool at every cell, takes the upper envelope of its tip shape as the surface it left,
  then drops the finishing tool onto that surface and onto the model. Cells where the finishing
  tool sits deeper on the model by more than max(0.002 in / 0.05 mm, cell/2) form the rest mask
  (the cell term absorbs the conservative heightmap's slope noise). The mask is grown by
  max(stepover, tool radius / 2), contoured and clipped to the boundary, and the chosen finishing
  pattern runs only there. It assumes the larger tool covered the whole area including its reach.
  If nothing is left and the operation has no roughing toolpath, it fails with a clear message.
- **cam-3d** — **Projecting 2D toolpaths onto a model (3d-project-2d).** `OperationSetup.projectOntoModelID`
  (optional, additive) is honoured in `AnyOperation.generate` for every kind except 3D Relief, so
  calculation, export and Check Toolpaths all see the projected moves. `ReliefProjection` (Ops3D)
  linearises arcs, subdivides cutting moves to the heightmap cell (0.01 in / 0.25 mm, capped like
  relief), and sets each point's depth to the toolpath tool's drop-cutter depth on the model plus
  its original depth below the material top; points are thinned within the document tolerance.
  XY rapids are unchanged (safe Z); vertical rapids below the material top are clamped to the top
  so a pass never rapids into material that was cleared somewhere else before projection. Outside
  the model's triangles the surface is its bottom plane (same as 3D Relief). Inspector:
  "Project onto 3D" picker under the vectors row, shown when the document has models.
- **cam-3d** — **Two-sided 3D machining (3d-two-sided).** `Relief3DParameters.twoSided` (optional): side
  (top/bottom), flip (left-right = turned over about the vertical centre line, X mirrored;
  top-bottom = Y mirrored), split depth (nil = halfway between the model's top and bottom) and
  web. It is per toolpath: make one Relief3D toolpath per side. The bottom side is computed in the
  flipped board's frame: models are mirrored in XY and Z with depths measured from the old bottom
  face, boundary vectors are mirrored, and the result is ordinary top-down G-code for the flipped
  board (same XY origin and Z-zero rules). The top side's surface is clamped at the split depth;
  the bottom side stops `web` short of it (default 0.04 in / 1 mm), so the part stays attached by a
  thin web instead of being released. Registration relies on stock cut exactly to the job size and
  pushed against the same corner; there are no registration-pin toolpaths yet. This is independent
  of a job-level two-sided setup (`io-two-sided-setup`), which is owned by another area.
- **cam-3d** — **Rotary / wrapped toolpaths (3d-rotary): not implemented, by decision.** The Avid
  PRO6096 has no rotary axis, the Mach4 post has no A-axis output and nothing could be tested on the
  machine, so emitting wrapped A-axis G-code would be untestable and unsafe. Left as missing (P3).

## toolpaths-2d (parity round 1)

- **toolpaths-2d** — tp-profile-last-pass: `ProfileParameters.lastPass: ProfileLastPass?` (nil = off, so old files decode). When on (closed vectors cut outside/inside, allowance > tolerance), every roughing pass is offset by an extra `allowance`; after ALL roughing loops the tool cuts the true offset once more, inner loops first, in the opposite direction when `reverseDirection` is set. By default the last pass is one lap at the full cut depth (`fullDepth`), otherwise it repeats the normal depth passes. Tabs, ramps and leads apply to the last pass as well. The last pass plunges from the material-top gap (not a rapid into the roughed slot), because the allowance strip is still standing there. Ignored for "On" and for open vectors.
- **toolpaths-2d** — tp-pocket-multi-tool: `PocketParameters.clearanceToolIDs: [UUID]?` (nil = use the legacy single `clearanceToolID`; the editor writes the list and keeps `clearanceToolID` equal to its first entry so older readers still see one tool). Tools cut in list order. A tool is ignored (with a warning on the finish toolpath) unless it is smaller than the previous used clearance tool and larger than the finish tool. The first tool clears the whole pocket; each later clearance tool does rest machining against the previous tool's radius and cuts the walls only near rest material (`PocketPlanner.restClearing(fullWalls: false)`); the finish tool still finishes the whole wall. Toolpaths are named "<name> (clearance N)" when there are several.
- **toolpaths-2d** — New operation kinds `OperationKind.engrave` / `.chamfer` with `AnyOperation.engrave` / `.chamfer` (additive enum cases; every switch over them is in CAMCore or KerfApp and was updated). Parameters live in the new file `Model/Parameters/ParametersToolpaths2D.swift` and the forms in `Panels/Toolpaths2DForms.swift` to keep shared-file edits small.
- **toolpaths-2d** — tp-quick-engrave: "Quick Engrave" cuts every selected vector on its centreline at a fixed depth (DepthSettings, so multi-pass works). It is generated by an "On" profile with no tabs/ramps/leads and retagged `.engrave`, so ordering and direction rules match Profile. The V-bit width preview is the groove width (`EngraveOperation.cutWidth`: V cone, ball radius, or diameter) shown live in the form and as toolpath metadata; the 2D canvas overlay still draws the centreline (the 3D preview shows the real groove).
- **toolpaths-2d** — tp-chamfer: "Chamfer" needs a V-bit/engraving bit with an angle. Size by width (default) or by depth: depth = vDepth(2·(width + tipClearance)); the tip runs on the vector, or `tipClearance` into the waste (outside = waste outside the vector, inside = waste inside, on = on the line). Implemented as a profile whose offset equals the tip clearance (allowance = clearance − radius), retagged `.chamfer`. A chamfer wider than the bit's cone (tip radius + depth·tan(angle/2) > radius) is an error. Metadata and the form show width × wall height × tip depth.
- **toolpaths-2d** — tp-profile-open-sides: `ProfileParameters.openVectorSide: OpenVectorSide?` (on / left / right of the vector's drawn direction; nil = on, as before). It is independent of the closed-vector side. The offset path (tool radius + allowance) is traced from Clipper's butt-ended outline of the polyline (`OpenOffset.oneSided`): the walk between the two end-cap corners on the chosen side. If that cannot be traced (self-crossing vectors, folds tighter than the offset) the vector is cut on the line with a warning. Passes still alternate direction with no retract, like on-the-line open cuts.
- **toolpaths-2d** — tp-pass-editor: `DepthSettings` gained `customPasses: [Double]?` and `exactStep: Bool?` (both optional, nil = the old evenly divided passes). Custom passes are absolute depths below the top; they are sorted, de-duplicated, clamped to (start, cut) and the cut depth is always the last pass, so a bad list can never cut deeper than the cut depth. Exact step keeps every pass exactly the pass depth apart and puts the remainder in the last roughing pass. "Last pass thickness" is the existing `finalPassDepth`. The form's "Passes" picker (Even / Exact step / Custom) lives in `PassEditor` and lists the resulting pass depths; switching to Custom seeds the list from the current passes. Every operation that uses `DepthSettings` (Profile, Pocket, Fluting, Engrave) gets it.
- **toolpaths-2d** — tp-profile-start-point: `ProfileParameters.startPoint: ProfileStartPoint?` (nil = nearest, the old optimised behaviour). `vectorStart` rotates each closed loop to the point nearest the start node of the source vector closest to it, and stops open vectors being reversed. `left/right/bottom/top` start at the middle of that side of the loop's own bounding box. Loops are still visited in the same order; only their start point changes. Applies to the last pass too.
- **toolpaths-2d** — tp-profile-order: `ProfileParameters.order: ProfileOrder?` (nil = nearest neighbour, as before; also: selection order, left→right, bottom→top, grid). Each loop is ranked by its outermost containing loop ("part"), so a part's holes are cut right before the part; inner-before-outer precedence is never broken. Left→right/bottom→top use the part's bounding-box min X / min Y; grid bands parts into rows from the bottom (row height = median part height) and goes left→right in each row (not serpentine). Selection order matches each loop to the nearest selected vector (setup.shapeIDs order). Loops still start at the point nearest the previous position unless a start point is chosen.
- **toolpaths-2d** — tp-sharp-corners: `ProfileParameters.sharpCorners: Bool?` switches the profile offset from round joins to Clipper miter joins (limit 4× the offset; sharper corners are squared off at that distance). The part's external corners stay sharp either way; the option makes the tool run out to the square corner instead of rolling round it (square waste corners, no dwell on the corner). Applies to outside and inside cuts (island corners) and to the last pass.
- **toolpaths-2d** — tp-pocket-profile-pass: `PocketParameters.profilePassFirst: Bool?` (nil = after, as before). `PocketStrategy.raster(angle:profilePass:)` is unchanged so files and other users (V-Carve flat area, 3D roughing) are untouched; only the Pocket form shows Profile pass None / First / Last. "First" cuts the wall contour of each region before its raster lines at every depth pass.
- **toolpaths-2d** — tp-helical-hole: new `OperationKind.holeMill` ("Hole Milling") with `HoleMillParameters`. One hole per closed vector (arc-only paths: exact centre and radius; others: bounds centre and the smaller bounds side; concentric paths keep the largest), or a fixed diameter for all. Helical bore: helix at (hole − tool)/2 from the start depth down to the cut depth, at most the depth-per-turn (default the tool stepdown) per revolution, then one flat lap and a move back to the centre before retracting; climb = counter-clockwise. A hole the tool's size is a straight plunge; smaller holes are skipped with a warning. Thread mill (internal only): plunge at the centre (a pilot hole is required, the form says so), feed out, whole turns at the thread pitch — climb right-hand goes up counter-clockwise from the cut depth, conventional goes down clockwise ending at the cut depth, left-hand does the opposite along Z at the same rotation (climb comes down, conventional goes up; see thread-mill hand, issue #96). Helices are emitted as line segments within the chordal tolerance (no helical G2/G3), so every post handles them.
- **toolpaths-2d** — tp-prism: new `OperationKind.prism` ("Prism Carve", V-bit only). The surface a V-bit leaves when its tip follows an outline at depth D is −D + distance/tan(half angle), so each connected shape (outer loop + its holes) is cut by running the tip along its outline at D = vDepth(2 × largest inscribed radius): the flanks meet at the material top at the widest point and form a ridge along the centreline (narrower parts get a lower ridge). The inscribed radius comes from a binary search on inward Clipper offsets. D is capped by the bit (cone wider than the tool: flat top + warning) and by the optional max depth. The outside of the outline is a matching V bevel; no separate clearing. Multi-pass at the pass depth, continuous round each loop.
- **toolpaths-2d** — tp-templates: `CAMCore/Templates/ToolpathTemplate.swift` (new folder). A template (`.kerftoolpaths`, pretty JSON, `formatVersion` 1) stores every toolpath with its vector references stripped (shape IDs, manual tabs, relief boundary), the units its lengths are in, a copy of each tool used, and a `VectorSelector` per toolpath = the most common layer name of its original vectors (matched case-insensitively) + closed / open / any. Applying (Toolpaths → Apply Toolpath Template…) adds every toolpath with a fresh id, converts lengths to the document's units, picks all vectors on that layer of that kind, renames on clashes ("Name 2"), and adds template tools the project and library do not have to the project's tool snapshot. Toolpaths with no matching vectors are still added (reported, so the user can select vectors); 3D reliefs take the design's first model or are skipped. Save is Toolpaths → Save Toolpath Template… (all toolpaths).
- **toolpaths-2d** — tp-tool-groups-materials: `Tool.group: String?` ("/"-separated folder; nil = listed under its type, as before) and `Tool.materials: [MaterialCuttingData]?` (RPM, feed, plunge, pass depth, stepover per material name, in the tool's units; `converted(to:)` scales them). `JobSetup.material: String?` names the job's material (Job Setup → Material type, with a menu of the names tools know). `CAMContext.tool(_:)` applies the matching material entry (case-insensitive) before unit conversion, so every operation picks it up; tools without an entry keep their defaults. The tool list shows named groups (alphabetical, "A › B") before the type sections. All new fields are optional, so old tools.json and .kerf files decode unchanged.
- **toolpaths-2d** — tp-feeds-calculator: `CAMCore/Tools/FeedsAndSpeeds` (feed = RPM × flutes × chip load, the inverse forms, and surface speed in SFM or m/min). The tool editor shows the current chip load and surface speed and has a target chip load field with "Apply" to set the feed rate. No built-in chip-load tables (they depend on the bit maker); the user enters the value from their chart.
- **toolpaths-2d** — tp-tool-edit-per-toolpath: `OperationSetup.toolOverride: ToolOverride?` (optional RPM, feed, plunge, pass depth, stepover in document units). `AnyOperation.generate` puts it in `CAMContext.toolOverrides` for the primary tool only, so the generators, the toolpath's tool copy, the post header and time estimates all see the changed values and the tool database is untouched. The inspector shows it as "Tool overrides" under the tool picker. Unit conversion of a project scales the override.
- **toolpaths-2d** — tp-keepout: `Document.keepOutZones: [KeepOutZone]?` (outline polygon in the material frame + height of the obstacle's top above the material top). Zones are made from selected closed vectors in Toolpaths → Keep-Out Zones… (default height 1 in / 25 mm; name and height editable; undoable) and drawn hatched red on the canvas. They are a safety check, not an avoidance planner: `KeepOut.violations` samples every move (rapids and arcs included) and reports a toolpath that comes within tool radius + 0.05 in (1 mm) of a zone while lower than its top + the same margin. `GCodeExporter.export` adds these as errors, so Export, Save All and Check Toolpaths all show them (Save All asks before writing files with errors). Toolpaths are not re-routed round zones; the user moves the clamp or the vectors, or raises safe Z.
- **toolpaths-2d** — tp-array-copy: `OperationSetup.arrayCopy: ArrayCopySettings?` (columns × rows at X/Y spacing, any operation). `AnyOperation.generate` repeats each generated toolpath's moves shifted by every grid offset (arc centres too) in one toolpath, rows in serpentine order; each copy already starts and ends at safe Z, so the joins are safe-Z rapids. Vectors are not copied. Copies whose cuts leave the material add a toolpath warning (the validator only checks machine travel, not material bounds). Shown in every toolpath's inspector under "Array Copies"; spacing scales with unit conversion.
- **toolpaths-2d** — tp-merge: new `OperationKind.merge` / `MergeOperation` holding copies of the merged operations (`MergeParameters.children`), so a merge is self-contained in the .kerf file. Toolpaths → "Merge With Next Toolpath" only merges a toolpath with the one directly after it when both have the same primary tool (no reordering, so no new safety risk); repeating it grows the merge, "Split Merged Toolpath" (or the inspector button) puts the parts back. Generation runs each child (with its own overrides/arrays) and joins consecutive results with the same tool and RPM into one toolpath; a clearance tool inside a pocket stays its own toolpath. A merged toolpath containing a profile keeps `kind = .profile` so group-by-tool export never moves it earlier. 3D reliefs are not mergeable. Templates store a merge as its separate parts.
- **toolpaths-2d** — tp-inlay-straight: new `OperationKind.straightInlay` (end mill). Both parts are cut from one matched outline M = close(open(S, r), r) (Clipper offsets by ∓r/±r), so the pocket's rounded inside corners and the plug's rounded concave corners agree. The pocket is an offset pocket of M to the pocket depth; the plug is an outside profile of M shrunk by `clearance` to the plug depth, optionally mirrored about M's bounding-box centre. Toolpaths are tagged `kind = .inlay` with `part` metadata so the existing validator error for pocket + plug in one program applies. New Toolpath → "Straight-Wall Inlay (Pocket + Plug)" adds a Pocket operation and a disabled Plug operation (as the V-carve inlay wizard does). No tabs on the plug (it is cut to the plug depth, not through).
- **toolpaths-2d** — tp-moulding: new `OperationKind.moulding`. The toolpath's vectors are rails; `MouldingParameters.sectionShapeID` is a separate cross-section vector (when created with 2+ vectors selected, the last selected is the section; the inspector can also set it). The section's bounding box maps X to the distance from the rail and Y to height (its top = material top); its upper envelope is sampled. Passes run along rail offsets (open rails: `OpenOffset` to the left/right; closed rails: inward) every stepover across the width; each pass depth is a 1D drop-cutter of the tool shape (ball, flat or V) against the section, flat beyond its ends, so the tool never cuts below the profile. Exact for straight rails; curved rails apply the section along the offset normals (no 3D surface/heightmap). Optional roughing cuts every pass limited to stepdown levels first. Templates drop the section reference (the user sets it again).
- **toolpaths-2d** — Not implemented this round (left clean, no UI): tp-drill-bank — the Avid PRO6096 has one spindle and Mach4 has no drill-bank head to drive, so there is nothing to output. tp-tiling — the 60 × 96 in bed takes full sheets; tiling needs every cut split at tile edges with fresh plunges and an indexing workflow, which is a safety-sensitive change with no use on this machine. Both stay "missing" in PARITY.md.
- **toolpaths-2d** — PARITY.md rows for the items above were updated (status + evidence); the totals line at the top was left for the integrator to recount after merging the parallel branches.
## app-ux

- **app-ux** — **Machines are separate from posts.** `MachineDefinition` (PostCore) holds the bed/Z travel (`MachineLimits`), spoilboard allowance, optional rapid rate, max feed and RPM range, and the list of compatible post ids. `KerfProject.machineID` is optional (older files decode; nil is not written). Resolution: the chosen machine, else the first machine whose posts include the job's post, else none (the post's own limits, as before). `KerfDocument.postProfile` is the post with the machine's limits converted into the post's units, so validation, export, time estimates and the preview all use the machine envelope. Built-ins: Avid PRO6096 (same limits as the Avid posts, so existing jobs validate identically) and Generic GRBL. User machines are JSON in `~/Library/Application Support/Kerf/machines/` (same id overrides a built-in). Picking a machine switches to its default post (matching document units) only when the current post does not drive it; both changes are one "Change Machine" undo step. Choosing a post is now "Change Post Processor". Job Setup warns when the material is larger than the bed or thicker than Z travel.
- **app-ux** — **Preferences** (Kerf ▸ Settings…, a SwiftUI `Settings` scene) are `AppPreferences`, stored as individual `kerf.pref.*` UserDefaults keys (invalid values fall back to defaults). They seed *new* documents only: units, grid spacing per unit, default machine and post (a default post that does not drive the default machine is ignored), and the snapping toggles of each new window. Canvas colours (material, selection, rapids) apply live. The Machines tab lists machines; built-ins are read-only and "Duplicate" makes an editable custom copy saved as JSON. `kerf.groupByTool` stays where it was (export sheet toggle).
- **app-ux** — **Autosave and crash recovery.** Saving still goes through `DocumentGroup` (system autosave/versions). On top of that, `RecoveryCoordinator` writes a recovery copy (`Recovery/<window id>.kerf` + `.json` metadata in Application Support/Kerf) of every open document whose project differs from the last opened/saved state (`KerfDocument.lastSavedProject`, moved by `confirmSave` once the file holds a save, see "Save confirmation" below), every 60 s by default (Preferences: off/30 s/1/2/5 min). Copies are removed when the document becomes clean, its window closes, or Kerf quits normally (only this session's own copies). Copies left at the next launch mean Kerf did not quit normally: an alert offers Recover (opens each copy as a new untitled document via `NSDocumentController.duplicateDocument`), Not Now, or Discard. Recovered/discarded copies move to `Recovery/Archive` (newest 20 kept) instead of being deleted. File ▸ Recover Unsaved Work… re-offers them. The original file path is not recorded (`ReferenceFileDocument` does not expose it), so recovered work is always "Save As".
- **app-ux** — **Help** is built in, not an Apple Help Book (a help book needs an indexed bundle; the app is built with SwiftPM only). `HelpTopic` holds Kerf's own Markdown text per topic; Help ▸ Kerf Help (⌘?) opens a searchable Help window. Forms and inspector sections have a "?" (`HelpLink`) that opens their topic: every toolpath type, tabs/ramps, Job Setup, export, Save All, Check, Inlay wizard, 3D placement, tool database, node editing, arrange, preferences and machines. `NumberField`/`LengthField`/`OptionalLengthField` fall back to `FieldHelp` tooltips keyed by label when no explicit help is passed.
- **app-ux** — **Welcome window and samples.** Help and Welcome are AppKit `NSWindow`s hosting SwiftUI (`HostedWindows`), not SwiftUI `Window` scenes, so they can be opened from the app delegate at launch, from sheets and from menus without an `openWindow` environment. The Welcome window shows at launch (Preferences toggle, also on the window itself) and from Help ▸ Welcome to Kerf: New, Open, "Open the Sample Sign", Getting Started help, and six quick-start steps. `scripts/bundle.sh` copies `samples/` into `Kerf.app/Contents/Resources/samples`; unbundled runs fall back to the checkout's `samples/` (found via `#filePath`). The sample sign opens as an untitled copy (`duplicateDocument`) so the shipped file is never overwritten; DXF/STL samples are revealed in Finder for File ▸ Import.
- **app-ux** — **Accessibility.** The canvas `NSView` is a VoiceOver group ("Design canvas") whose value summarises the job and whose children are one element per visible vector (up to 400), labelled with kind, size, position, layer and state (`CanvasAccessibility`, pure and tested); pressing an element selects the vector. Tab / Shift-Tab on the canvas select the next / previous editable vector (one stop per group, wrapping) and announce it; Control-Tab still moves focus out of the canvas (standard AppKit convention for views that use Tab). Icon-only buttons (layer eye/lock/colour, toolpath visibility/status/calculate, check, delete, tool database, tool palette) have explicit accessibility labels. Contrast: canvas material, selection and rapid colours are adjustable in Preferences; SwiftUI controls follow the system Increase Contrast setting.
- **app-ux** — **Side-by-side view.** `CenterMode.split` ("2D | 3D" in the toolbar picker, View ▸ Show 2D and 3D Side by Side, ⌥⌘2) shows the design canvas and the 3D simulation in an `HSplitView`; both observe the same document, so edits and recalculations update both. Actions that need the canvas (tab editing, STL placement) call `showDesignCanvas()`, which keeps the split instead of forcing 2D.
## layout

- **layout** — True-shape nesting (`CADCore/Layout`, Design > Layout > Nest Parts…) is a raster nester written from general CAM knowledge. Each part is rasterised on a square grid after growing it by half the part spacing plus half a cell diagonal, so two parts whose cells do not overlap are always at least the spacing apart. Parts are placed largest first, at the lowest and then leftmost free position over all allowed rotations. A free-run table per grid row lets a span be tested with one lookup and lets the scan jump over whole occupied stretches. Grid size comes from a precision setting (Draft 250k, Normal 1M, Fine 3M cells per sheet, so about 0.07 in on a 48x96 sheet at Normal). Gaps are therefore slightly larger than the spacing, never smaller.
- **layout** — A part is a group (`groupID`) or a loose shape, plus every selected shape inside its outer outline (holes, pockets, text, drill marks), so features move and rotate with their part. Small parts may nest inside holes of larger parts (option). Unselected visible vectors are obstacles by default. Copies beyond the first are new shapes, and they are added to every toolpath that cuts the original. Parts that do not fit stay where they were, and the sheet reports them.
- **layout** — The operator job sheet (File > Export Job Sheet…) is a printable HTML file opened in the default browser, so it prints with the system dialog and needs no PDF code. It lists the material, the Z-zero and XY-origin instructions, safe Z and home, a tool table, and the toolpath order in program order (the shared "group by tool" setting). Each tool change is marked "Load T#". For each step it shows the maximum depth below the material top and the estimated time, and there is a tick box per step. It also has an SVG preview per sheet with an X0 Y0 marker. Stale toolpaths are recalculated first. Failed or uncalculated toolpaths are listed as warnings. This also covers the `io-setup-sheet` row.
- **layout** — Material checks live in `PostCore/Validation/LayoutChecks` and are all warnings, because the cut may be intended. They flag visible vectors that are wholly or partly outside the material, material larger than the post profile's X/Y travel, and toolpaths whose cutting moves (below the material top) put the tool centre more than one tool radius outside the material. Tracing a part that sits flush with the edge is therefore fine. G-code export, Save All and the job sheet report the toolpath check. Check Toolpaths shows a "Material and machine" section first, but only when it has issues, so the existing section order is unchanged for clean jobs. Spoilboard depth and travel span were already validator errors.
- **layout** — Nesting overflow uses additive `Layer.sheet: SheetSlot?` (sheet number and current offset; optional, so older files decode). Sheet 1 is every shape that is not on a sheet layer. Sheets 2… are layers "Sheet N", parked to the right of the material (the slot index skips the active sheet; the gap is 8% of the larger material side). Design > Layout > Sheet on Material swaps which sheet sits on the material by moving shapes, so it is one undo step. CAM (`ToolpathCalculator`) ignores parked shapes through `NestSheets.activeDocument`. One set of toolpaths therefore serves every sheet: show a sheet, then export its G-code. A toolpath whose vectors are all parked fails with a message that says how to cut them. Parked sheets are not reported as "outside the material". The job sheet gets one section per sheet with that sheet's parts. Nesting always shows sheet 1 on the material first. Job Setup unit conversion also scales sheet offsets.
- **layout** — Clamps and fixtures are layers with an additive `Layer.keepOut: KeepOutZone?` (clamp height above the material top). Their closed vectors are keep-out zones, so they can be drawn and edited with the normal tools. Layout > Clamps and Fixture Holes… adds clamp footprints along the edges (on a "Clamps" layer) or a hole grid. Holes can be screws to keep clear of (a "Screws" keep-out layer) or holes to drill (a plain "Fixture Holes" layer for a Drilling toolpath). A layer's context menu turns it into a keep-out layer or back. Keep-out shapes are never machined, never move with sheets, and are not "outside the material". Nesting treats them as obstacles on every sheet. The exporter reports an ERROR when the cutter, radius included, enters a zone below its top while cutting or on a rapid, for example a rapid at safe Z over a clamp taller than safe Z. Toolpaths are not re-routed automatically.
- **layout** — Tiling (Toolpaths > Save Tiled G-code…) works on calculated toolpaths (`CAMCore/Layout/ToolpathTiling`). The job is split into equal tiles no larger than the requested size, which defaults to the post profile's X/Y travel. Feed moves are clipped to each tile with Liang–Barsky. Arcs that cross a seam become lines, and arcs inside a tile stay arcs. Where a cut leaves the tile the cutter retracts to safe Z, and it re-enters with a rapid at safe Z, a rapid to just above the material and a plunge at the tool's plunge rate. Outer job edges are not clipped. Overlap re-cuts a band of that width centred on each seam. Each tile is its own program in a lower-left origin tile job (same Z setup). The header title says where to zero X/Y on the material ("zero XY at material X… Y…"), which is the registration: the operator measures from the material corner. No registration holes or marks are generated. Each tile is validated in its own frame, with the design moved too, so keep-out and material checks line up. The P3 tiling is relevant only for boards over 60 in wide or 96 in long.
- **layout** — Part labels (Layout > Label Parts…) are ordinary text outlines on a "Part Labels" layer. Each one goes at the point of the part furthest from every edge (outline, holes and features: a refined 25x25 grid search) and is shrunk to fit that clearance. Labels below the smallest height are skipped and reported. Parts are found the same way as for nesting. Unnamed parts are named "Part N" so the job sheet, the labels and the parts agree. Labelling again replaces the earlier labels on those parts. The dialog can also create a V-Carve toolpath for the labels. The job sheet lists every sheet's parts by name and prints the names on the preview. Labels and keep-out zones are not listed as parts.
## io (round 1)

- **io** — Job sheet (io-setup-sheet): File → Job Sheet… writes a self-contained HTML page (inline CSS, preview PNG as a data URI) and opens it in the default browser, which handles printing and PDF. Content: material size/thickness, units, Z zero, XY origin, safe/home Z, post, total time, tool changes, tool list in program order (with a tick column for the operator), one row per toolpath (tool, diameter, rpm, feed/plunge, deepest cut, time) and warnings for uncalculated/failed toolpaths. Order and grouping follow the shared "group by tool" setting. `JobSheet` (pure) and `DesignSnapshot` (offscreen CG picture of material, vectors, toolpaths and origin) live in `KerfApp/Model`.
- **io** — PDF / AI import (io-ai-pdf-import): `PDFImporter` (CADCore) walks page 1's content stream with `CGPDFScanner` (path construction, paint, q/Q, cm, Form XObjects). Each painted path = one shape; clip-only (`W n`) paths and text are skipped with a warning; extra pages are reported. Crop box lower-left = (0,0), points → document units. `.ai` files stay routed to `EPSImporter`, which now hands `%PDF` data (Illustrator 9+) to `PDFImporter` instead of rejecting it; legacy PostScript AI still uses the EPS interpreter. Image XObjects (JPEG, or raw 8-bit Gray/RGB/CMYK) can be extracted as PNG + placement rect via `importPage(includeImages:)`.
- **io** — Bitmap import (io-bitmap-import): JPG/PNG/BMP/TIF/GIF/WebP/HEIC (anything ImageIO decodes) become `PlacedImage`s stored PNG-encoded in `Document.images` (optional, so older files decode and design-only files stay small). Placement: the file's physical size when it records a DPI other than 72, else fitted to 90% of the material; centred. Images go on a "Bitmaps" layer (layer visibility applies), default 40% fade, and never feed toolpaths. `rect` is the full image; `crop` (unit-square fractions, bottom-left origin) hides parts of it. Edited from the Design sidebar's "Images" section (popover: position/size with aspect lock, Fit to Material, fade, crop %, visibility, delete; one undo step per Apply). Drawn on the canvas under the grid and vectors, and in the job-sheet picture. PDF/AI import now also brings in embedded images. Unit conversion scales image rectangles.
- **io** — OBJ import (io-obj-3d-import): `OBJImporter` (CADCore) reads `v`/`f` only (fan-triangulated polygons, `v/vt/vn` and negative indices), reuses the STL vertex merge, assumes millimetres like STL, and treats the file as Y-up (most modellers' OBJ default), mapping (x, y, z) → (x, −z, y) so the model's up axis becomes the relief height. `OBJImporter(yUp: false)` keeps Z-up. In the app `.obj` goes through the same "Place 3D Model" dialog as STL. Other formats (3MF, FBX, DAE…) are not read; export them to STL/OBJ.
- **io** — Job templates (io-job-templates): a template is an ordinary `.kerf` project in `~/Library/Application Support/Kerf/templates/` (job setup, layers, vectors, toolpaths, post, tool snapshot). File → Save as Template… writes one (default folder = templates; the name becomes the menu title, `/ : \` replaced). File → New from Template lists them and opens an *untitled* copy through SwiftUI's `newDocument` action, so Save never overwrites the template. "Open Templates Folder" is there for renaming/deleting. Toolpath results are not stored; press Calculate All in the new job.
- **io** — Two-sided jobs (io-two-sided-setup): `JobSetup.twoSided: TwoSidedSetup?` (flip axis left–right or top–bottom, optional bottom-side Z zero) and `Layer.side: JobSide?` (nil = top), both optional so older files decode. Each side's vectors are drawn in that face's own frame *as seen from above while it faces up*, so toolpaths need no coordinate transform and the XY origin means the same corner of whichever face is up; the other side is only shown mirrored (about the material centre line of the flip axis) as dashed grey for registration. An operation's side comes from its vectors' layers; vectors on both sides are a calculation error. Bottom-side toolpaths are generated with the bottom Z zero. Design → Show Top/Bottom Side (⌥⌘F) switches the edited side (selection cleared; picking, Select All and new shapes stay on the shown side). Export G-code (All), Save All, Check, the tool-change summary, the 3D preview and the job sheet all work on the shown side's operations (`KerfDocument.outputProject`), so each side is posted separately; a single-toolpath export uses that toolpath's own side. Enabling two-sided adds a "Bottom Side" layer; layers move between sides from their context menu. 3D models are top-side only, and the 3D preview simulates one side at a time.
- **io** — Plunge Z and datum offset (io-material-plunge-z): additive optional `JobSetup.plungeGap` ("Plunge Z", height above the surface the tool rapids down to before feeding) and `JobSetup.datumOffset` (machine X0Y0 = chosen corner/centre + offset, folded into `originInMaterialFrame` so `MachineCoordinates`, the canvas origin marker and the validator all follow). nil keeps every existing default, so golden G-code is unchanged: 2D builders still use 0.05 in / 1 mm above cleared material, 3D/fluting/texture 0.04 in / 1 mm, and V-carve still plunges from safe Z; when set, all of them rapid to the plunge gap (capped at safe Z) before feeding. Job Setup validates 0 ≤ plunge Z ≤ safe Z. The post header prints an "XY datum offset" comment only when an offset is set.
- **io** — Model position in material (io-model-position): the Place 3D Model dialog's Z section now works in gaps: "Gap above" (= the old Z offset) and "Gap below" (thickness − offset − model height) are both editable and drive each other with the model height fixed; Top / Centre / Bottom buttons anchor the model; "Fit Depth Between Gaps" stretches the model height to fill the material between the gaps; a small side-view diagram shows the band (red when it overruns the material). No model change: `PlacedModel.zTop/depth` still store it.
- **io** — Multiple sheets (io-multiple-sheets): the sheet being worked on always lives in `Document.job`; other sheets are parked in `Document.otherSheets` (`MaterialSheet` = id, name, own `JobSetup`), with `activeSheetID/activeSheetName/sheetOrder` and `Layer.sheetID` (nil = the primary sheet, fixed id). All optional, so older files decode. Switching sheets swaps the jobs (Design → Sheets, one undo step); because everything else already reads `document.job`, the canvas, Job Setup, two-sided settings, export and job sheet follow the current sheet without further changes. Shapes/layers/toolpaths of other sheets are hidden and not pickable; the sidebar lists only the current sheet's layers. An operation's sheet comes from its vectors' layers (vectors spanning sheets = calculation error); each operation is calculated with its own sheet's job, so results stay valid across switches (they are marked stale because the design revision changes, and export recalculates). Toolpaths without vectors (3D relief) and 3D models belong to the primary sheet. Export/Save All/Check/job sheet cover the current sheet only — one G-code program per sheet. Add Sheet copies the current material setup and adds a layer for it; Delete Current Sheet (confirmed, undoable) removes its layers and vectors.
- **io** — SVG text and images (io-svg-text): replaces the cad-io "skip with a warning" rule. `<text>` is outlined with CoreText into one shape per element: `font-size` is the em (point) size in user units (unlike Kerf's own text tool, which sizes by cap height), `font-family` lists are tried in order (generic families map to Helvetica / Times New Roman / Menlo…, bold weights try the "Bold" face first, a missing font falls back to Helvetica with a warning), `text-anchor`, `<tspan>` x/y/dx/dy, inherited properties from ancestors, collapsed whitespace. Not supported: CSS classes from `<style>`, `textPath` geometry (its text is set on a straight line), letter-spacing, vertical text. `<image>` with a `data:` URI becomes an `ImportedImage` (axis-aligned bounds of its placement, `preserveAspectRatio` ignored); linked image files are skipped with a warning. `ImportResult` gained `images` (defaulted), PDF import now fills it too, and the app places every importer's images as tracing images.
- **io** — SketchUp (io-skp-import, partial): `.skp` is a proprietary binary format; reading it needs Trimble's SketchUp SDK (licensed download, not vendorable here), so Kerf does not read it. Instead `DAEImporter` reads COLLADA (.dae), which every SketchUp edition exports (File → Export → 3D Model): triangles/polylist/polygons, node matrix/translate/rotate/scale, `instance_node` components, `<unit meter>` and `<up_axis>` (Y_UP/X_UP turned to Z-up). It goes through the same Place 3D Model dialog as STL/OBJ. Choosing a `.skp` in Import shows how to export DAE or STL. 2D SketchUp import (faces as vectors) is not done.
- **io** — EPS / AI / PDF export (io-eps-ai-export): `PDFExporter` (Core Graphics PDF context) and `EPSExporter` (hand-written EPSF-3.0 using only moveto/lineto/curveto/closepath/setrgbcolor/stroke) share the SVG exporter's page rule (min(0, bounds.min)…bounds.max, in points), stroke each shape in its layer colour with a 0.5 pt hairline, and convert arcs to ≤90° cubics. Hidden layers are not written. `.ai` is written as PDF — Illustrator opens PDF-format files, and Kerf's AI importer reads it back; no Illustrator private data is produced. `FileFormats.exporter(forExtension:)` picks the exporter; Export Vectors chooses by the file extension typed.
- **io** — Document variables (io-document-variables, partial): `Document.variables: [DocumentVariable]?` (Design → Document Variables…) plus built-ins `width`, `height`, `thickness`, `safez` from the current job. Every `NumberField`/`LengthField`/`OptionalLengthField` (toolpath forms, Job Setup, drawing panels…) parses through `ExpressionEvaluator`: `+ − * / ^ ( )`, unary minus (looser than `^`), case-insensitive names, an optional leading `=`, and unit suffixes `in` `"` `mm` `cm` that apply to the product before them ("1/4in" in a mm job = 6.35). The table and units reach the fields through SwiftUI environment values set on the document window. Values are evaluated when typed — fields do not stay linked to the variable, so changing a variable later does not update parameters already entered (linked parameters would need every parameter struct to store expressions; left for later).
- **io** — Print (io-print, 2D only): File → Print… (⌘P) prints the shown sheet/side — material, visible vectors, tracing images, calculated toolpaths (when Show Toolpaths is on) and the origin marker — fitted to one page (orientation follows the material); File → Print at Actual Size… prints 1:1 tiled across pages (paper templates). It replaces SwiftUI's default Print item. The 3D preview is not printed directly (SceneKit views do not print reliably); the job sheet carries a picture for that purpose.
- **io** — File thumbnails (io-file-thumbnails, via custom icons): a Quick Look thumbnail extension needs an `.appex` bundle (extension entry point, sandbox entitlements, plug-in registration) that a SwiftPM-only, Command-Line-Tools build cannot produce and test reliably, so instead each save sets the design picture (256 px: material, vectors, tracing images of the shown sheet/side) as the file's custom Finder icon. `KerfDocument.snapshot` schedules it 1.5 s later (the write happens after the snapshot), using the window's `documentConfiguration.fileURL`. The icon is written inside an `NSFileCoordinator` metadata-only write with the open NSDocument as the presenter, and the exact modification time (ns) is restored afterwards, so the document never sees an external change. Custom icons live in xattrs, so they are lost when the file goes through tools that strip them (some cloud/zip/git). Disable with `defaults write com.seanperkins.kerf kerf.fileThumbnails -bool NO`.
## drawing-r1 (VCarve drawing parity, round 1)

- **drawing-r1** — New drawing dialogs share one `DocumentSheet.drawing(DrawingSheet)` case and live in `Panels/DrawingSheets.swift`; their commands are in a separate "Vectors" menu (`App/VectorMenuCommands.swift`) and `Model/VectorCommands.swift`, so shared files (KerfCommands, ContentView, KerfDocument) only get one-line additions.
- **drawing-r1** — **Dog-bones** (`CADCore/Editing/Dogbone.swift`) modify the selected vectors in place (provenance becomes `derived`). "Parts" relieve corners that are concave for the shape's region (holes read even-odd, so a part's holes are relieved too); "Openings" relieve the convex corners of slots/pockets. The relief is a cutter-radius circle through the corner point: dog-bone = centre on the bisector, T-bone = centre on the longer/shorter adjacent edge. Only line–line corners up to a max angle (default 135°) are relieved; a relief that would run past the end of its edge is dropped.
- **drawing-r1** — **Arrays** copy the selection's whole groups; each copy gets its own group IDs (as Duplicate does). Rectangular spacing is either a gap between bounding boxes or a centre-to-centre offset; columns run +X and rows +Y (negative distances reverse). The original and all copies are selected afterwards.
- **drawing-r1** — **Vector validator** (`CADCore/Editing/VectorValidator.swift`, Vectors › Validate Vectors…) checks the selection, or every visible shape when nothing is selected, for zero-length vectors/segments, nearly closed vectors (ends within 20× the unit tolerance: 0.01 in / 0.2 mm), open vectors (report only), duplicates/overlaps (a path whose every sampled point lies within tolerance of another path; of two identical paths the later is reported, otherwise the shorter) and self-intersections (flattened polyline crossing, adjacent segments ignored). "Show on Canvas" selects the shapes and circles each problem (`KerfDocument.highlightMarkers`, cleared from the sheet or the menu). Fix closes, deletes or splits (self-intersecting closed outlines go through a union, which flattens curves) on editable layers only.
- **drawing-r1** — **Editable text**: `Shape.text: TextSpec?` (optional, no file-version bump) keeps the string, font, cap height, justification, line spacing (× natural line height), letter spacing (CoreText kerning) and a layout→document transform. `Shape.transformed` now also composes that transform, so moved/scaled/rotated/mirrored text re-outlines in place; sizes shown in the inspector are layout sizes × the transform's uniform scale. The click point is the first baseline's left/centre/right point by justification. Node edits (`KerfProject.editNodes`), in-place vector commands and "Convert to Curves" clear the spec; older text shapes (no spec) are plain vectors. Re-editing is one "Edit Text" undo step via the inspector's Apply button (⌘↩).
- **drawing-r1** — **Arc tool** (A): "3 points" = start, end, then a point on the arc; "Centre" = centre, start (radius), end direction, always counter-clockwise. Arcs are true `.arc` segments. The inspector also creates an exact arc from centre, radius and start/end angles (sweep sign = direction; 360° makes a closed circle).
- **drawing-r1** — **Typed entry while drawing**: with a drawing tool active, digits/`.`/`-` start a buffer on the canvas (`,`, `<` and spaces extend it; Delete edits, Esc clears, Return applies). Box tools: `W,H` (one value = square) anchored at the pointer as lower-left corner, or at the drag start in the drag's direction. Radial tools: `R` or `R<angle` centred at the pointer. Polyline/curve/arc: first entry `X,Y` absolute, then `ΔX,ΔY`, `length<angle`, or a length towards the pointer. Letters keep working as tool shortcuts. The canvas keeps its extra state in one `CanvasDrawingState` stored property.
- **drawing-r1** — **Set start point** (node inspector "Set Start"): rotates a closed vector's editable form so the selected node becomes node 0; direction is unchanged. Node editing shows each selected vector's start and direction as a green arrow. Fluting already walks closed vectors from their start; whether Profile honours it (rather than its own lead/start choice) is up to cam-2d — TODO(cam-2d) if wanted.
- **drawing-r1** — **Mirror…** (Vectors menu) flips left↔right or top↕bottom about the selection centre, the material centre, or the selection's left/bottom or right/top edge, optionally as a copy (original kept, copy selected). The quick Mirror buttons/menu items still mirror in place about the selection centre. Live text stays editable when mirrored (its transform is mirrored).
- **drawing-r1** — **Trim** tool (X): a click deletes the clicked span of the nearest editable vector between its neighbouring crossings with any visible vector (or itself); a vector with no crossings is deleted whole; a closed vector becomes one open vector. **Trim to Boundary…** keeps the parts of the targets inside/outside the first selected closed vector (targets = the other selected shapes, or every editable shape). Crossings are found on flattened geometry (`CADCore/Editing/PathSplitting.swift`) and the segments are then split exactly at that parameter (lines/arcs stay lines/arcs, cubics via de Casteljau), so cut points are accurate to the unit tolerance.
- **drawing-r1** — **Fillet / Chamfer** (Vectors menu, or "Fillet…" in the node inspector) works on corners between two straight segments: the selected nodes while node editing, otherwise every such corner of the selected shapes. Fillets are tangent `.arc` segments; chamfers cut the same distance along both edges. A corner whose trim would overrun its edge (or meet the neighbouring corner's trim) is skipped instead of producing a broken vector. Rather than a separate click-a-corner tool, single corners are chosen with node editing.
- **drawing-r1** — **Guides**: drag from the top ruler (horizontal) or left ruler (vertical) to add a guide; with the Select tool, drag a guide (where no shape is under the pointer) to move it, or back onto a ruler to delete it. Guide positions snap to the grid (⌘ disables). Guides are saved in the file as `Document.guides` (optional, older files decode) and are undoable. Snapping order: object points, then guides and horizontal/vertical "extension" lines through existing nodes (each axis separately, the other axis falls back to the grid), then the grid. Extension lines are only H/V alignment through nodes (not tangent extensions of open ends). Vectors › Snap to Guides toggles both; Clear Guides removes all.
- **drawing-r1** — **Measure** tool (M): drag between two (snapped) points for distance, ΔX/ΔY and angle; click a vector for its path length, bounding W×H and — when the clicked segment is an arc or the shape is a parametric circle — radius/diameter and centre. The reading is drawn on the canvas and listed (selectable) in the inspector; it is view state (`KerfDocument.measurement`), not saved. Radii of curves made of Béziers are not estimated.
- **drawing-r1** — **Circular array**: N items in total (original included) around the material centre or a typed point, either spread evenly over an angle (360° does not repeat the first position) or at a fixed step; copies are rotated about the centre or, with "Rotate copies" off, only moved round the circle.
- **drawing-r1** — **Fit Curves to Vectors** (`CADCore/Editing/CurveFit.swift`) greedily replaces runs of points with the longest line or circular arc that keeps every point (and every chord midpoint) within the tolerance; arcs are at most 180° and must progress monotonically round their centre. Output is lines + arcs only (no Bézier fitting) because arcs post as G2/G3. A shape is only replaced when the segment count drops, so clean drawn geometry is left alone.
- **drawing-r1** — **Delete Duplicate Vectors** (Vectors menu) runs the validator's duplicate/overlap check on the selection (or the whole visible design) and deletes the redundant paths in one undo step, then reports the count. Only a path lying entirely on another one counts; partly overlapping paths are not split.
- **drawing-r1** — **Fit Text to Box** scales (proportionally, or stretched) and centres the selected live text inside the bounding box of the other selected vector, or the material when only text is selected, less a margin. The text stays editable (the fit is part of its transform). Fitting is to the boundary's bounding box, not its exact outline.
- **drawing-r1** — **Text on Curve / Arc**: the selected live text is laid character by character along the other selected vector (from its start, centred, or to its end; offset to the left of the curve's direction; "other side" reverses the curve), each character rotated to the curve's direction at its centre. Without a curve it is bent round a circle of the given radius ("arch up" over the top, "smile down" under the bottom), centred where the text was. The result is plain vectors (a new shape); the live text is deleted unless "Keep the original" is on. Multi-line text is laid as one line.
- **drawing-r1** — **Single-line font**: "Kerf Single Line" (`CADCore/Editing/StrokeFont.swift`) is an original stroke font drawn for Kerf (no third-party font data): A–Z, 0–9 and common punctuation as open centre-line strokes (O, 0, 8 and dots are small closed loops) on a cap-height grid. Lowercase uses the capitals; unknown characters show as "?". It is listed first in the font pickers and is a normal live-text font (`TextSpec.fontName`), so justification, spacing, fit-to-box and text-on-curve work with it. Engrave it with a Profile "on the line" (or a V-bit at fixed depth).
- **drawing-r1** — **Trace Bitmap…** (`CADCore/Editing/BitmapTracer.swift`): the image is decoded with ImageIO to grayscale (transparency = white) at a chosen resolution, thresholded (dark = ink, or inverted), ink specks and enclosed holes under N pixels are removed (4-connected flood fill), pixel-edge outlines are traced (diagonal-touching pixels stay separate), simplified with Douglas–Peucker (px tolerance) and corners softened by limited corner cutting (≤ 0.6 px per pass, so straight edges keep their place). The result is one closed multi-path shape, scaled to the typed width and centred on the material. The image itself is not kept in the document (no bitmap layer yet).
- **drawing-r1** — **Freehand** tool: the drag is sampled every 1.5 screen points (unsnapped), simplified with Douglas–Peucker at 1.5 screen points and turned into a smooth Catmull-Rom Bézier curve through the remaining points; ending within 8 screen points of the start closes it.
- **drawing-r1** — **Node extras**: "To Arc" replaces the segment after each selected node with a circular arc through its start, middle and end (a straight segment bows a quarter of its length to its left); because node editing works on the Bézier form, the arc is stored as its cubic approximation. "Align X/Y" moves the selected nodes onto their average X or Y. Mirror-mode (symmetric) node editing is not implemented in this round.
- **drawing-r1** — **Shear / Distort…**: shear is an affine transform about the selection centre (angles under 89°; live text stays live). Envelope moves the four bounding-box corners by typed offsets and maps the vectors bilinearly (flattened, mapped, refitted as lines/arcs at the unit tolerance), so live text becomes curves. Dragging envelope corners on the canvas is not implemented; the corner offsets are typed.
- **drawing-r1** — **Extend to Nearest Vector** (Vectors menu): each free end of the selected open vectors is extended straight along its exact end tangent to the first crossing with any other visible vector (up to twice the larger material dimension). A line end is lengthened in place; a curved end gets a new line segment. Ends that would hit nothing stay as they are.
- **drawing-r1** — **Offset Open Vectors…** (separate from the closed-shape Offset… sheet, which is app-shell's): left / right (relative to each vector's direction) / both sides make parallel open copies — corners opening away are rounded, others mitred, then refitted as lines and arcs; "closed outline around" uses the existing `PathOps.offsetOpen` (round ends). One new shape per source shape. Loops from offsetting tight curves by more than their radius are not cleaned up.
- **drawing-r1** — **Straight-wall inlay offsets**: the selected closed design is unioned, then opened and closed by the end-mill radius (offset −r/+r, then +r/−r), so convex and concave corners are both rounded to r — the only outline both a pocket (cut inside) and a plug (cut outside) can reproduce. The pocket vector is that outline + clearance/2, the plug − clearance/2, mirrored left↔right by default (glued face down) and placed to the right of the design. Output is two new shapes; toolpaths are left to the user (Pocket + outside Profile).
- **drawing-r1** — **Copy Along Vector…**: the last selected shape is the guide (select objects, then shift-click the guide); the other selected shapes (with their groups) are copied so their joint bounding-box centre sits on evenly spaced points (open guide: both ends included; closed guide: start not repeated), set by count or by distance apart, optionally rotated to the guide's direction (the original counts as facing +X). Originals are deleted unless kept.
- **drawing-r1** — **Nested groups** (supersedes "flat groups"): `Shape.groupID` stays the outermost group (so click-selection, moves and every existing caller are unchanged) and the new optional `Shape.innerGroupIDs` remembers the groups underneath, outermost first. Grouping shapes that are already grouped nests their groups; grouping exactly one existing group again does nothing. Ungroup (⇧⌘G) now removes one level; Vectors › Ungroup All Levels clears every level. Copy/paste/arrays remap inner group IDs too; pruning after deletes peels levels left with a single member.
- **drawing-r1** — **Dimensions**: `Document.dimensions` (optional `[DimensionAnnotation]`, saved, undoable, scaled with unit changes) holds aligned/horizontal/vertical (two points + click for the line position), radius/diameter (click an arc or parametric circle) and angle (corner + two arms) dimensions. They are not shapes, so toolpaths, booleans and vector export never see them. Values are live from the stored points (they do not follow later edits of the geometry). Drawn in purple on the canvas; listed with delete buttons in the Dimension tool's inspector.
- **drawing-r1** — **Kerning / letter adjustments**: `TextSpec.letterAdjustments` (optional) moves and/or rotates individual letters (numbered across lines, newlines not counted; numbering follows glyphs, so a font ligature counts as one letter). With adjustments the text is laid out glyph by glyph (same positions as the normal layout when nothing is moved). Editing is numeric in the text inspector ("Letter spacing by hand": letter number, move X/Y, rotate) rather than by dragging letters on the canvas; text stays live. Text on Curve ignores the adjustments.
- **drawing-r1** — **Vector Texture…**: fills the selected closed vectors (even-odd, together) with straight lines, sine waves or zigzags at a spacing and angle; waves/zigzags have amplitude, wavelength and a 0–1 "variation" that randomises each line's amplitude and phase with a fixed seed (same result every time). Lines are offset half a spacing from the centre and clipped with Trim-to-Boundary; the result is one shape of open vectors to cut on the line.
- **drawing-r1** — **Boundary Around Selection…**: bounding rectangle (+ margin), convex hull (monotone chain over the flattened points, grown by the margin with round joins) or shrink-wrap (union of the closed regions — open vectors as hairline outlines — grown by gap+margin then shrunk by gap, outer loops only, so gaps narrower than 2×gap are bridged). Adds one new closed shape.
- **drawing-r1** — **Plaque Border…**: generated sign outlines (rectangle, rounded, chamfered, notched = quarter-circle cut-ins, ogee = convex-then-concave quarter rounds, oval) around the selection's bounds plus a margin; the oval is scaled by √2 so the content's corners stay inside. Optional inner border line (offset inwards) is a second path of the same shape. Original corner styles designed for Kerf; arcs are true `.arc` segments.
- **drawing-r1** — Everything in this round lives behind the new **Vectors** menu, the node inspector, the drawing-tool inspector and five new canvas tools (Arc A, Freehand, Trim X, Measure M, Dimension). Not done this round: dragging envelope corners / letters on the canvas (numeric instead), mirror-mode node editing, Bézier curve fitting, a kept bitmap layer for tracing.

## toolpaths-2d (parity round 2)

- **toolpaths-2d** — tp-tool-db-import-export: `CADCore/Persistence/ToolLibraryExchange.swift`. Tool Database → Share ▸ Import Tools… / Export All Tools… / Export Selected Tool…. Two formats picked by file extension: `.kerftools` (pretty JSON `{formatVersion: 1, tools}`, lossless incl. groups and per-material data; a bare `tools.json` from another Mac is also accepted; newer format versions are refused) and `.csv` (header row, columns in any order, only name/type/diameter required, types and units matched by raw value or display name, no per-material data). `ToolLibrary.merge(_:policy:)`: identical tools (same id and contents) are skipped; a tool with the same id but different settings is Replace / Keep Both (new id, " (imported)" suffix on a name clash) / Skip, chosen in a dialog only when such conflicts exist; new tools are added. Tool numbers stay unique: an incoming tool whose T number is taken gets the smallest free number and the import summary lists it, so two cutters never share one T word after a merge.
- **toolpaths-2d** — tp-tool-shapes: no new `ToolKind` cases (other modules switch over it exhaustively, and parallel branches would break on merge). Instead `Tool.shape: CutterShape?` (new file `CADCore/Model/CutterShape.swift`; nil = the plain shape, so old files decode): `.bullNose(cornerRadius)` on end mills, `.taperedBallNose(tipRadius, halfAngle per side)` on ball noses (the diameter is the widest cutting diameter where the taper ends), `.form(points: [height, radius])` on end mills or ball noses. `Tool.effectiveShape` ignores a shape on the wrong kind or with invalid values (the editor warns), and `Tool.heightAboveTip(atRadius:)` is now the one cutter-outline function: the simulator (`ToolShape.shaped`), the 3D drop-cutter (`CutterProfile.Shape.shaped`), Moulding's 1D drop-cutter and Quick Engrave's groove width all use it, and the 3D preview draws the outline as stacked frustums. Form outlines are reduced to "lowest height at which the outline reaches radius r" (a top-down heightfield cannot hold undercuts). 2D Profile/Pocket still offset by the diameter (the outline only changes the floor/corner shape, which is what a bull nose is for). Moulding's drop-cutter now also tests the section's corner points (a vertical step could otherwise be gouged between samples) and samples the tool at 97 points instead of 49. CSV export carries corner_radius / ball_tip_radius / taper_half_angle; form outlines are only kept in `.kerftools`. Tool Database → Add Tool has Bull Nose End Mill / Tapered Ball Nose / Form Tool, and the editor's Shape section has a roundover preset and a side-view outline.
- **toolpaths-2d** — tp-keepout (round 2): zones can now re-route toolpaths. `KeepOutZone.liftOver: Bool?` (nil/false = check only, as before), a "Lift over" toggle per zone in Toolpaths → Keep-Out Zones…. `KeepOutAvoidance` (CAMCore/Ops2D/Support) runs last in `AnyOperation.generate` (after array copies and 3D projection) for every operation: wherever the tool (radius + the export check's clearance, plus a few tolerances so the check never fires on the boundary) would be over a lift-over zone below its top + clearance, the cut stops, the tool rapids straight up to the clearance height (highest lift-over zone top + 2 × clearance, never below safe Z), rapids across, rapids down to the clearance above the material top and plunges back at the plunge rate. Arcs that touch a zone are split into chords within the chordal tolerance; others stay arcs. Rapids that would pass over a zone too low are raised the same way, and the tool never descends inside a zone. A toolpath that would end parked over a zone travels back above its own first point (outside the zone) and finishes at its original last height there, so the next toolpath's first rapid never descends over the clamp. Material under the zone is left uncut by design (it is under the clamp); the toolpath's metadata shows "keep-out lifts". Plunging back is a straight plunge (no ramp) into at most one pass depth of new material; that is the price of a generic re-route and the reason it is opt-in per zone. Avoiding the zone by changing the cut shape (e.g. pocket boundary minus the zone) was not done: it would need per-operation changes and silently changes part geometry.
- **toolpaths-2d** — tp-drill-bank (round 2): still not done, on purpose. The PRO6096 has one spindle and Mach4 on the Avid drives no drill-bank head, so a multi-spindle planner would produce G-code nothing can run. Single-spindle drilling (peck, hole milling) covers the need.
- **toolpaths-2d** — tp-moulding (round 2): curved, cornered and closed rails no longer use the straight-rail 1D approximation (which gouged on the inside of bends: across the tool, points along the tangent are nearer the rail than the 1D model assumes). `MouldingSurface` rasterises the swept surface — depth = section depth at the distance from the rail on the moulded side (left/right of open rails by the nearest segment's side; inside closed rails by an even-odd scanline), section depth at the rail within the tool's reach behind it, the shallowest value where rails overlap, every cell holding the shallowest depth in its square via a sliding-window minimum of the section (so steps are honoured) — and each pass is densified to the cell size and dropped with the existing 3D `DropCutter` using the tool's real outline (so bull-nose/tapered/form tools work too), capped at the section's deepest point + start depth. Cell size = min(stepover/2, tool radius/4, section width/32), coarsened to keep ≤ 4M cells. Passes still follow the same rail offsets; only their depths change, now varying along the pass. ## cam-3d (round 2)

## app-ux (round 2)

- **ux-gadgets — Gadgets are JavaScript, run in JavaScriptCore.** VCarve's gadgets are scripts run from a Gadgets menu; Kerf's equivalent uses the JavaScriptCore framework that ships with macOS (no new dependency, no Package.swift change — `import JavaScriptCore` auto-links). The `kerf` API (`GadgetAPI`, written for Kerf, not modelled on any Vectric API) can read the selection, shapes, layers, tools, material, variables and typed parameters; draw rectangles/circles/ellipses/polygons/stars/polylines and free paths with arcs and Béziers; move/rotate/scale/delete shapes; create layers; set variables and the selection; and add toolpaths through `OperationFactory` (name, tool by name/number/id, depth for profile/pocket/drill, profile side).
- **Gadget safety:** the context has no file, network or process API, only `kerf` and `console`. Runs are stopped after 10 s through `JSContextGroupSetExecutionTimeLimit`, which JavaScriptCore exports but does not declare publicly; it is looked up with `dlsym` and skipped if missing. Runs are synchronous on the main thread (short scripts; the limit bounds the hang). A gadget works on a copy of the project: if it throws, nothing changes; if it succeeds, everything is one undo step ("Gadget: <name>"). Locked shapes / shapes on hidden or locked layers cannot be moved or deleted. At most 20,000 new shapes per run.
- **Gadget files:** `.js` files in `~/Library/Application Support/Kerf/Gadgets/` (Gadgets > Open Gadgets Folder writes a README with the API and an example `.js.sample`). Metadata lives in the leading `//` comment block (`@name`, `@description`, `@needs-selection`, `@param name type default "Label"` with types number, length, integer, bool, text, choice). Length defaults are written in inches and scaled for mm jobs; values reach the script in document units. A gadget with parameters (or header problems) opens a dialog sheet; one without runs immediately. Log lines and `kerf.message` text are shown in an alert after the run.
- **ux-gadgets scope:** three built-in example gadgets (Hole Grid, Frame Selection, Rosette). Not done: gadgets that show their own custom UI, run toolpath calculation or export G-code, or persist settings between runs (the dialog resets to the declared defaults); no Lua compatibility with Vectric gadgets. The Gadgets menu is its own `GadgetCommands` so it merges without touching KerfCommands.
- **fix round 2 — keep-out lift-over across toolpaths.** `KeepOutAvoidance.apply` still runs per operation, but the export now treats the program as one move stream. `KeepOut.violations` and the clamp-layer `LayoutChecks.keepOut` carry the position from one toolpath's last point to the next toolpath's first point while the tool stays the same, so the post's travel between toolpaths is checked. (An XY rapid from below safe Z is modelled as the post does it: up to safe Z, then across.) After a tool change the XY is unknown, because the controller may have moved during the change. Checking restarts there and that travel is neither flagged nor re-routed; the operator owns the tool-change position. `GCodeExporter.export` runs `KeepOutAvoidance.link` on the final ordered list first. Where the travel crosses a lift-over zone too low, it prepends rapids to the next toolpath: straight up to the clearance height, then across. Every export path (Export, Save All, Check, tiled, batch) goes through `export`, so they all get it. The 3D preview shows the unlinked travel.
- **fix round 2 — lift-over resumes at the true start.** The router keeps the original previous target (`prev`) apart from the lifted tool position (`cur`) and re-routes every move from `prev`. After a lift, the tool rapids at the clearance height to where the cut really resumes, then plunges at the plunge rate. Before this fix it ramped from the clearance height down to depth at full feed, which left the cut short of depth beyond the zone.
- **fix round 2 — Tool Database edits save as they are made.** The editor commits each change to tools.json (`ToolLibraryModel.commitEdit`, which only writes when the stored tool differs and never brings back a deleted tool) and once more when it closes. Switching tools or closing the window can no longer lose an edit. The Save button is gone. "Revert Changes" goes back to the settings the tool had when it was selected. Asking "save or discard?" was rejected: it adds a modal in the middle of browsing tools, and the rest of the app saves preferences without asking.

- **parity (round 3, 2026-10-20)**: Re-checked the six partial/missing PARITY items against main (unchanged) and added nineteen P3 items from Vectric's public product page, help index and V12.5 What's New. Drag knife joins drill bank, laser and rotary as won't-do for the spindle-only Avid. The machine setup wizard stays partial on purpose: Kerf ships with the Avid preset and does no online machine lookup.

## fix round 3 (keep-out home move, pass depth, tiled zones)

- **fix round 3 — keep-out zones, the move home and tool changes.** The footer's move home is a fixed path, so `GCodeExporter.export` now models it: from the last toolpath's end, up to safe Z, then to Home Z if the footer uses `{HOME_Z}`, then across to home XY if it uses `{HOME_X}`/`{HOME_Y}` (Z first, as the built-in footers do; a custom footer that does something else is not modelled). This travel runs through both keep-out checks as a rapid-only "Move home (end of program)" toolpath, so a check-only zone or clamp taller than Home Z in the way is an error ("raise Home Z"). For lift-over zones, `KeepOutAvoidance.linkTravel` appends the lifted travel (up to the clearance height, across, down to Home Z at home) to the last toolpath, and the footer's own moves then go nowhere. The tool-change position is still unknown, but its first XY move no longer happens at safe Z when any keep-out zone or clamp (+ 2 × the 0.05 in / 1 mm clearance) is taller than safe Z: `PostJob.approachHeight` makes the post climb to that height after each M6 (and at the start), cross to the first point, and only then descend. This is a few seconds of extra Z travel per tool change and nothing when no zone is taller than safe Z.
- **fix round 3 — non-positive pass depth.** A pass depth or tool stepdown of 0 or less is now an error ("Pass depth must be positive" / "Tool pass depth (stepdown) must be positive") in every operation that paces passes from it (profile, pocket, fluting, prism, moulding roughing, 3D flute, 3D roughing), via `DepthSettings.validatePassDepth`. `passDepths` itself is bounded at 10 000 passes so the forms' pass preview can never hang, and the pass-depth and tool-database fields show a red note for a value of 0 or less. A zig-zag ramp's length is floored at drop / tan(max angle) / 2 (two legs at the max angle; the smooth ramp floors at drop / tan the same way) and capped at 200 legs per pass. Cancelling a running generator mid-operation (a cancel flag threaded through every generator) was not done: no known input now produces unbounded work, and it would touch all sixteen generators; Stop still takes effect between operations.
- **fix round 3 — tiled export.** Each tile's project also moves `Document.keepOutZones` into the tile frame (clamp layers were already moved with the shapes), so keep-out checks and lift-over links line up with the clipped toolpaths in every tile.

## DXF import report (2026-10-20, docs from the forum research in learning-lab)

- **imp-1 — DXF import says when an outline stops just short of closing.** Users of Carbide Create and VCarve repeat one complaint: a DXF from a CAD program arrives fragmented or open, and Join then moves lines without saying which. Kerf already joins loose entities whose ends touch (0.0005 in or 0.01 mm), but a gap a hair wider than that left an open vector and no message, so the first sign was a toolpath that would not take it. `PathOps.nearlyMeetingEnds` now finds open paths with an end more than the join tolerance but no more than 100 times it (0.05 in or 1 mm) from another end; a path's own two ends count, so an outline that stops short of closing is found. `DXFImporter` adds one warning per layer ("Layer "Cabinet": 1 open vector has ends that nearly meet, 0.2 mm apart. The import joins ends within 0.01 mm, so it stayed open; a gap in the source drawing is the usual cause."), which the existing Import alert shows. Only near misses are reported: a lone open line (engraving, a V-carve centerline) is a normal thing to import and must not raise an alert, and ends further than 100 times the tolerance are more likely meant to be separate. The 100 is a judgment call (a slip of a few hundredths of an inch or about a millimeter); it is one constant, `DXFImporter.nearMissFactor`. A grid lookup keeps the search linear (6000 paths run in about 60 ms in the test). Not done yet: a tolerance the user can raise at import or in Join Open Vectors (the Join command uses a fixed 0.001 in or 0.025 mm), and a note of how far Join moved the ends; the message points at the cause, not a one-click fix. SVG, EPS and PDF imports do not report gaps yet.
- **imp-2 — Join Open Vectors takes a tolerance and says what it will do first.** The import report (imp-1) pointed at a gap but the only tool that could close it, Arrange ▸ Join Open Vectors, used a fixed 0.001 in or 0.025 mm and moved ends without saying by how much; users of Carbide Create describe exactly that ("you don't even know what was moved"). The menu item and the inspector's Join button now open a small dialog (`JoinVectorsSheet`, in the drawing-dialog frame) with a "Join gaps up to" field, starting at the old value, so pressing Return does what the command always did. Under the field it says, from `DesignCommands.joinPreview`, how many open pieces become how many vectors (closed and still open), the largest distance any end will be moved (`PathOps.joinOpenPathsReporting`, which counts the gap that closes a loop), and, when something stays open, the closest ends still apart with a hint to raise the tolerance above that. The preview recomputes when the field commits, not per keystroke, because joining is quadratic in the number of pieces. A dialog was chosen over a silent larger default because a wide tolerance can join things that were meant to be separate, and the user should see the number first. Locked shapes and closed shapes are left out of the preview and the join, as before. Not done: SVG, EPS and PDF imports still do not report gaps, and the import alert does not offer to open this dialog. The UI harness gained an `import` step (and `closeSheet` now also clears an alert) to check the alert and the dialog on screen; capturing an open alert exposed a bug where the accessibility-tree walker recursed until its background stack overflowed, now bounded by a depth cap and a seen-set.

- **imp-3 — SVG, EPS and PDF imports report near-miss gaps too.** imp-1 covered DXF only; the same slip arrives through every vector format, and SVG from Illustrator or Inkscape is the most common import of all. `ImportGaps.warnings` runs the same `PathOps.nearlyMeetingEnds` check (join tolerance 0.0005 in or 0.01 mm, near-miss window 100 times that, per layer) over an import's shapes, and the three importers append its warnings. The wording differs from DXF's on purpose: these importers do not join loose entities, so instead of explaining why a join did not happen it says what to do ("Arrange ▸ Join Open Vectors… closes it."). The three importers were not given DXF's joining step: their paths come from path data that is already one subpath per element, so fragments are rare, and joining would change what existing files import as. Running it over the SVG fixtures found a false report: a three-point test squiggle 2 px long whose ends are 0.03 in apart. `nearlyMeetingEnds` now counts a path's own two ends only when the gap is under a tenth of the path's length (`ownEndGapShare`); a square with a 1% gap is a slip, a scribble whose gap is as long as itself is not. Gaps between two different paths' ends are unchanged, because a fragmented outline is made of short pieces with small gaps. The shipped SVG, EPS and PDF fixtures raise nothing.

## Depth numbers (2026-10-20, from the forum research)

- **depth-1 — The Export sheet reads the deepest cut out of the G-code.** Users of other CAM programs describe a toolpath summary that disagrees with the G-code (a start depth, the wrong post, a different zero) and are told to open the file and read the first plunge. Kerf's Export sheet showed the Z-zero mode but no depth. `DeepestCut.find` now reads the finished program with `GCodeReader` and takes the lowest feed move, so the number is the file's, not the toolpath's; the depth below the material top goes through `MachineCoordinates.depth(ofMachineZ:)` (the single Z-zero helper), tested in both Z-zero modes with the same physical answer. The sheet shows "Deepest cut: Z -0.77 in (0.02 in below the material bottom)", or "at the material bottom", or "0.25 in above the material bottom" (tolerance 0.0005 in or 0.01 mm). Follow-up (same day): Save All Toolpaths shows each file's deepest cut under its tools, read from that file's posted program the same way, and the job sheet's setup table has a "Deepest cut" row computed from the toolpaths' lowest Z through the same `MachineCoordinates` helper (the job sheet does not run the post), tested to agree with the Export sheet's number in both Z-zero modes. Still open: the 15 "rapid plunge below the material top" warnings on the sample.

- **depth-2 — The Tabs field says what a tab really holds.** A commenter on another CAM program says its tabs are measured from the bottom of the cut, not the material bottom. Kerf's `TabSettings.thickness` is the same ("Tab height above the final cut depth", and `TabLayout.topDepth = cutDepth - thickness`) but the field was labeled just "Thickness", so a cut that went 0.02 in below the material to clear the spoilboard quietly left a thinner tab. The field is now "Tab height" with a tooltip, and `TabHold.note` says under it what the tabs hold: with a 0.77 in cut in 0.75 in material and 0.125 in tabs, 0.105 in; once the overcut reaches the tab height it warns that they hold nothing; a cut that stops above the bottom says tabs are not needed. Not done: a depth set to the stock bottom still does not follow a later thickness change (a new toolpath's depth is the thickness at that moment); this note is the only warning. The UI harness gained a `project` step and `harness/projects/sign-overcut.kerf` to show the overcut case.

- **depth-3 — A through cut follows the material thickness.** A new Profile's cut depth is the thickness at the moment it is made; change Job Setup to thinner stock afterwards and every profile quietly cut into the spoilboard, or to thicker stock and nothing cut through, with the Tabs note (depth-2) as the only hint. `DepthSettings.followsThickness` marks a depth that was set from the thickness; `OperationFactory` sets it on new profiles, and the Profile form's Cutting Depths section has a "Follow the material thickness" toggle with a caption saying how far past the bottom the cut stays. When `JobSetupForm.apply` changes the thickness (after any unit conversion), `DepthFollow.adjusted` moves every following cut depth by the same difference, so a through cut stays through and a 0.02 in overcut stays 0.02 in, and drops hand-edited passes that fall past the new depth. The depth stays absolute in the parameters: the generators, the validator and saved files see a number, not a rule, so nothing in CAMCore changes and older files load with the flag unset (fixed depths, as before). Only profiles get the flag by default: a pocket, flute or engrave depth is a design choice, not "through". Job Setup edits one sheet's stock, so only the operations on that sheet move (both sides of it), and the parts of a merged operation move one by one since each keeps its own depth. Not covered: a thickness changed by other code paths (sheet switching, templates) does not move depths; the dialog is where people change stock.

## Pause step (2026-10-20, from the forum research)

- **pause-1 — A toolpath can stop the machine for the operator.** Users of Carbide Create and LightBurn asked, four separate times, for a pause between toolpaths to flip the part, add clamps or clear chips; VCarve has nothing for it either, and people hand-edit M0 into the file. `OperationSetup.pauseAfter` (`PauseStep`: a message and an "optional stop" flag) is applied when the toolpaths are collected for a combined export (`GCodeExporter.withPause` puts it on the operation's last toolpath), not when the toolpath is generated, so turning it on or editing the message never makes the toolpath stale (`isStale` compares the operations without it) and a single toolpath's own file never carries it. The post writes it between toolpaths only: retract to safe Z, then the profile's `pause` template, by default `M5`, `(MSG, message)`, `M0` (or `M1`), then the same re-entry as after a tool change (modal state forgotten, Z restated at the approach height, the crossing to the next toolpath at that height when a clamp is taller than safe Z), and the next toolpath restarts the spindle and dwells. Nothing is written after the last toolpath, because the program ends there. The message is a `(MSG, …)` comment, which Mach3/4 and LinuxCNC display and GRBL senders echo; `asciiOnly` now also turns control characters into spaces, so a pasted line break cannot start a G-code line inside the message. "Group by tool" treats a pause as a barrier: a toolpath never moves ahead of one and a paused toolpath never moves. Merge with Next refuses an operation that pauses after itself (a merged operation is one toolpath, so the stop would vanish); the pause after the second operation becomes the merged operation's, children never carry one, and Split gives it back to the last part. The validator warns when any M0/M1 is reached with the spindle on or the tool below safe Z (a custom pause template could do either), judging the state at the end of the block because a controller runs a block's spindle word and motion before it stops; the shipped template trips neither. The header lists the pauses, the job sheet prints a highlighted row under the step, and the sidebar row shows a pause mark. Follow-up (same day): the time estimates (`ToolpathStats.estimatedSeconds`, the 3D preview's `SimulationTimeline`, so the sidebar, the preview and the job sheet agree) count a pause as a stop with the same allowance as a tool change, counted once when a pause ends in a tool change (`ToolpathStats.stopsBefore`), since the operator does both in one stop; the sidebar's tool-change summary lists each pause under the loads and says "N stops (tool changes and pauses)" in its tooltip. The allowance is the user's tool-change setting because a pause's real length is the operator's; a separate pause allowance would be a second number to tune for the same guess. Still open: the `pause` template is editable only in a saved post's JSON.

## Pre-flight checks (2026-10-20, from the forum research)

- **preflight-1 — The export warns about four mistakes a valid program hides.** Forum threads about other CAM programs describe the same ruined jobs: a through cut with no tabs that threw the part, two tools sharing a number so the wrong one was loaded, a 3D model deeper than the stock, and a tool named "1/4 in" with a 1/8 in diameter. The G-code validator cannot see any of them: the program is well formed. `PreflightChecks` adds them as warnings to the same issue list the Export sheet, Check Toolpaths and the job sheet already show, never as a modal alert, because each has a legitimate reading (vacuum or tape hold-down, a deliberate name) and people on those forums resent being stopped by dialogs they must dismiss every time. Loose part: a Profile toolpath with tabs off whose cut depth reaches the material thickness (within the usual tolerance) on at least one closed vector; the message counts the closed vectors. Tool numbers: among the tools in the exported program, two with one number but different kind, diameter or angle; the same geometry under two library entries is not reported, and the check is on the program, not the library, because that is where the same T word for both tools does the harm. Names: every size written in the name (fractions, decimals with `"`, in or mm, bare fractions) is compared with the diameter and, for V-bits and engraving cutters, the tip diameter, which is what their names quote; only a name whose sizes all disagree is reported, so "1/4 shank 1/8 end mill" and "60° V-Bit 1/2"" pass and the shipped library raises nothing. Models: any placed 3D model whose lowest point is below the material bottom. The loose-part check looks inside merged operations, since the exported toolpaths point at the merge while each part still makes its own cut with its own tabs and depth. Not done: a check that the selected post matches the document's units is already the validator's; nothing checks that the clamps in Fixtures are where the operator put them, and the Tool Database does not yet flag library-wide duplicate numbers.

## Deep review (2026-10-20, docs/REVIEW-2026-10-20.md)

- **Build and test through the scripts.** SwiftPM compiles `Package.swift` under its own `sandbox-exec`, and macOS refuses to nest one sandbox inside another, so `swift build` from an agent shell failed before it started. `scripts/swiftpm-env.sh` probes with a trivial `sandbox-exec` and adds `--disable-sandbox` only when that fails; nothing changes for a normal terminal. SwiftPM's sandbox only guards the manifest and plugins, so nothing is lost for this package. A new `scripts/build.sh` wraps `swift build` the same way; AGENTS.md names it as the build command.
- **The finishing lap inherits the roughing tabs.** Automatic tabs are laid out from a loop's start, and the last-pass loops start wherever the roughing ended, so their tabs drifted away from the roughing tabs and the lap severed them. Instead of forcing the finishing loop to start where the roughing started (which would change the cut order and the lead-in), `ProfileOperation.cutLoops` returns the material-frame tab centres it placed and the finishing call projects them onto its own loops (within the allowance plus a few tolerances), the same way manual anchors already work. Manual tabs were unaffected.
- **An arc shorter than two output digits is written as a line.** Rounding to the post's precision can make a tiny arc's end coincide with its start, and every controller reads that as a full circle at cut depth. A true full circle has length 2πr, so the length test cannot mistake one for the other.
- **NaN is refused, not formatted.** `String(format:)` prints `nan`, every comparison in the validators is false for NaN, and controllers differ on what `Xnan` does. The post throws `nonFiniteMove` and the importers drop or reject non-finite numbers at the parse boundary, so the question never reaches the writer.
- **Clipper exceptions stop at the C boundary.** A C++ exception unwinding into Swift aborts the process; the wrapper returns null and `GeomKernel` drops paths with a coordinate Clipper cannot scale (non-finite or beyond 1e10), which no real drawing has. A zero-width offset of an open path is empty rather than the input closed into a polygon (Clipper returns the input unchanged for delta 0).
- **Missing operations are export errors.** A program with a step silently left out is the most dangerous kind of "valid" G-code (the part comes free before it is drilled). Every route (Export, Save All, Save Tiled) now carries an `.error` issue per enabled operation without toolpaths, so the existing "Save Anyway" confirmation gates it. The same mechanism reports a project post that is not installed on this Mac, and the substitute id is no longer written back into the project.
- **A single toolpath is exported with the job it was calculated for.** `outputProject(for: .operation)` used the shown sheet's job; it now uses `machiningJob(for:)`, which is what the calculator uses, so thickness, Z zero, safe Z and the footer's home agree with the moves.
- **Deleting a layer never changes what a shape is.** Shapes move to an ordinary layer on the same sheet and side; a keep-out layer's outlines are deleted with it rather than becoming machinable vectors that the keep-out check no longer covers.
- **Golden files never regenerate without the flag.** A missing golden used to be written from the current output and compared with itself. Now `KERF_UPDATE_GOLDEN=1` is the only write path and a missing file fails the test.
- **Render smoke tests sample colours.** A blank PNG of a 560x680 view is about 1.5 KB, so `data.count > 1000` tested nothing; `AppTestSupport.looksDrawn` counts distinct sampled colours instead.

- **harness-clips** — Product clips (`docs/images/*.gif`, `*.mp4`) are generated, not screen-recorded: a `reel-*.json` scenario drives the debug app through the UI harness with `record` / `endRecord` around its steps, and `scripts/reel.sh` stitches the frames with ffmpeg. Reasons: a clip can be regenerated after any UI change with one command; nothing needs Screen Recording permission; and the person at the Mac keeps their focus, because the window is parked past the screen's edge and drawn as key through the key/main notifications instead of activating the app. The frames come from the window server (`CGWindowListCreateImage` of the app's own window, 12 to 20 ms a frame at 2x) because `cacheDisplay` of the whole window took 260 ms and starved the run loop. Clicks are `NSEvent`s posted to the app's queue (a direct `sendEvent` of the press leaves a row's tracking loop waiting for a release that never comes) and find their control through the Accessibility API, preferring an exact title, naming a field by its label, re-reading until the frame is stable (it used to add the enclosing scroll view's top inset, which SwiftUI left out of the inspector's frames; superseded by inspector-ax-frames below). Row selection in a window that is not really key is done in code behind a drawn pointer. ## Validator (2026-10-21, issue #36)

## File sets (2026-10-22, issue #11)

- **file-set — Save All and Save Tiled write every file or none, and ask before replacing.** Both wrote one file at a time, so a failed post was skipped silently, a mid-set failure left a partial set, and existing files were overwritten unasked; on a tiled job that is a missing tile nobody notices until the sheet is cut. `GCodeFileSet` is the one path. It writes nothing while a program failed to post, a name is not one plain unique file name, a planned name is a folder, or a file is there that the user was not asked about. Otherwise it writes every program into a hidden working folder inside the chosen one and renames each into place, the file that was there going first into the working folder's `was/`. Renames, not `replaceItemAt`: the create and both renames are exclusive where the volume allows it (an exclusive hard link stands in where it does not, and only a volume with neither gets check-then-rename), so a file a sync client drops in mid-save stops the save instead of being lost. ## Tabs (2026-10-22, issue #9)

- **tab-warnings — a profile warns when its tabs are not what was asked, and posts anyway.** A loop too short for the requested count got fewer tabs, down to none, and a manual anchor on a deleted vector or on another part attached to whichever loop was nearest. Either left a part free on the last pass with nothing said. An anchor belongs to a vector and travels with it, so it attaches only where the loop the toolpath would cut for its part runs through one of the toolpath's loops, and is reported otherwise: another part's anchor however near, an open vector's, or one whose loop the offset swallowed or merged away is never moved. The part is the vector plus every selected closed vector that overlaps or nests with it as drawn, or whose offset at that pass joins it (each offset alone on the side its nesting in the selection puts it, so a hole's loop moves into the hole), offset together: a hole imported as its own shape, two overlapping shapes, or two parts closer than the tool get the loop the toolpath cuts, not what each would get alone, while a neighbour the tool fits between is not part of it. The anchor must lie on the part's outline (the edge two touching vectors share is inside the part, except on a cut on the line, which follows each vector as drawn; where vectors cross, the stretch inside the other is still an edge of the even-odd region and is cut, on the far side), and the part's loop nearest it must be one offset from its own vector and within the miter limit's reach (straight across from its stretch, or at the corner that trims or extends it; farther means its stretch collapsed, or an inside corner sharper than about 29 degrees): a hole smaller than the tool in a part whose outer loop survives is reported, not moved to the outer loop. Nearest-loop-within-a-bound and vertex-distance tests were tried first and failed on mitered loops and near-touching parts. Each last-pass loop finds its roughing loop by offsetting the last-pass loops together by the allowance and taking the roughing loop through the rebuilt point one allowance across from one of its edges: a loop with none lays out its own tabs and counts its shortfall; one whose roughing loop had tabs that did not reach it is reported, since laying out fresh tabs there would bridge nothing. ## Pocket coverage (2026-10-22, issue #15)

- **pocket-coverage — an offset pocket covers everything the tool can reach, to within 2% of the diameter, and a test proves it.** Concentric rings a stepover apart cover the floor between them only while the next ring is within reach. A coverage test (`Ops2DPocketCoverageTests`) rasterises the floor a round tool can reach (the pocket shrunk by the tool radius and allowance and grown back by the radius, so the sliver in a sharp inside corner does not count) and fails on any point farther than the radius plus `PocketPlanner.coverageSlackFraction` (2%) of the diameter from every cut. It found two real gaps, both at a stepover over about half the diameter. At a sharp 90 degree corner the worst point on the diagonal is 0.59 stepovers from the nearest ring, so a scallop shows from a stepover of 85% of the diameter (6% of the diameter at the 95% cap). At the narrow tip of a wedge or lobe the last ring ends well short of the point the tool can reach; a wedge of 8 to 35 degrees left a stud up to a stepover minus the radius wide (0.108 in with a 1/4 in tool).
- **The fix.** `PocketPlanner.coverageCleanup` finds the uncovered floor (the reachable area minus the sweep of the rings, with the slack) and cuts the pieces of the ring halfway between the rings that lie in the zone around that floor. With a stepover under the diameter every point is within half a stepover of the half ring, so one halving suffices; the cleanup measures what is still farther than the slack from every cut afterwards and, if that is more than a sliver, the pocket carries a warning, and a clearance tool in that state does not hand over to the next tool's rest machining (the next tool then clears everything itself). The pieces keep the direction of the ring they come from and take the rank of the ring just outside them, so they wait for the ring just inside. A clean pocket gets nothing extra, and the cleanup is skipped when the stepover is no more than the radius plus the slack (every point is then within one stepover of a ring, at a corner or a tip too) or when the planner's radius is zero (relief roughing plans tool-centre paths and its finishing pass cleans up). It applies to `PocketOperation`'s offset strategy, for the finish tool and the first clearance tool alike; the rest-machining rings of later tools (`restClearing`) are not changed. Default tools (40%) and every golden file are unchanged.
- **What is not covered on purpose.** Raster pocketing is covered when it has its profile pass; without one the wall is left to the user's finishing pass, and the test does not ask for more. The 2% slack is the product's coverage promise apart from `allowance`; it is a fraction of the diameter, with a floor of two context tolerances for very small tools.

## V-carve glyphs (2026-10-22, issue #14)

- **vcarve-glyph-test — V-carve is proved on real letters, by what it carves, not by how its skeleton is wired.** `VCarveGlyphTests` carves A-Z, a-z, 0-9 and & @ % in five installed fonts (Times New Roman, Helvetica, Snell Roundhand, Avenir Next Condensed, Impact) at capital heights of 0.25, 1 and 2 in with the 60 degree bit, and judges the toolpath against the letter worked out from the font's own contours alone: a point is inside when an odd number of contours enclose it (even-odd, which is the font's own nonzero fill here because no contours of these fonts overlap) and its distance to the edge is its distance to the nearest contour, with no union and none of the region the operation builds. It asserts: the cut has length and every piece of the letter (the dot of an i, the halves of a %) has cut in it; at every sampled point inside the glyph the groove has taken out the depth the outline allows there (the distance to the nearest edge, up to the bit's radius, since a stroke wider than the bit is cleared flat at its full depth) to within 2% of the letter's height; every point of every contour lies within 1% of the letter's height plus two chord tolerances of some groove's edge (which sees a hairline or serif the interior grid steps over); at every sample the groove has its axis inside the letter, and at every end of a move (a plunge or a lift included) and at every sixth sample between it is no wider than the outline allows there (within 10% of it plus half a percent of the height and three chord tolerances), and where the bit moves sideways is no narrower either (the guard against overcut, which cannot be repaired on the router, and against a region built per shape that would carve counters as filled discs); and the runs of cutting moves form as many connected cuts as the glyph has connected pieces (an O is one ring). Runs that share a vertex are one cut. Otherwise two runs are joined where one groove reaches the other's axis and the floor between the axes is carved: at a reflex corner (the junction of a serif or arm with a stem in Times New Roman k) the Voronoi diagram's link from the stem's axis to the corner is a secondary edge the medial axis leaves out, so the two pieces of the axis touch only at a point where the groove has no width, and nothing is left uncarved; a gap that leaves a ridge, or two strokes that are merely close, is not a join.
- **What it found.** No dropped or split letter, but two real defects. The stroke simplifier (`VCarveStrokes.simplified`) compared each point with the segment from the last kept point to the next raw point, so a long shallow arc drifted by many tolerances: a hairline of Snell Roundhand's L at 2 in was cut with a groove 0.013 in wide centred on the outline, 0.012 in off its axis. It now calls the Douglas-Peucker `Polyline3D.simplify`, so every point it removes lies within the tolerance of the segment that replaces it (unit test `vcarveSimplifiedStrokesStayWithinToleranceOfTheOriginal`; a first fix that grew each segment point by point checked every point against the segment and was quadratic on a large black area). The V-carve parts of the sign sample's G-code (the `golden/sign-*.tap` files and `samples/sign.tap`) keep about 12% more moves along curved axes (the V-carve section grows from 1,052 to 1,179 move lines) and are regenerated; the diff is coordinates only. `MouldingOperation.simplify` has the old flaw (issue #68). The other defect is in ordering: with "selection order" on, the strokes of the shape selected first that have two points (the spurs from a corner of a flattened curve to the skeleton) were cut after every selected shape, because the stroke was assigned to a shape by its middle vertex, which for two points is the end on the outline, and no region contains its own outline. `VCarveOrdering.group(of:)` now looks at the middle of the middle segment for the region test and keeps the vertices for the open-vector test; `vcarveSelectionOrderFollowsTheSelectedLetters` (an O and a B selected in both orders) is the regression test.
- **Checked by mutation, by hand.** Dropping one edge in 41 of the medial axis fails the carve, outline and connection checks in every font; making the engine cut 15% too deep fails the overcut check, an extra feed plunge 0.1 in deeper at the end of a good carve fails it too (`vcarveGlyphJudgeCatchesAnExtraDeepPlunge`), and the old simplifier fails it in Snell Roundhand. The width check has a floor: a groove up to 10% wider than the outline allows, plus half a percent of the height and three chord tolerances, passes, which is about 1.3% of the height (0.026 in at 2 in) on a hairline, and a stroke thinner than about that can be traced at zero depth (the undercut check has the same floor), so a defect smaller than that is not caught. O, B and 8 are also carved with each contour as its own shape in every order, with and without "start at the vectors' start points" and "selection order"; because the operation carves one region built from all the shapes, that matrix guards against a region built per shape and against strokes lost in the ordering, not against a different carve. A machine missing most of the fonts fails `vcarveGlyphFontsAreInstalled` instead of passing by carving nothing. The test takes about 30 s of the CAMCore suite (the grooves and outline segments are bucketed on grids; a plain scan costs minutes in a debug build) and asks CoreText for outlines one at a time through a lock local to the file: with a dozen test threads asking at once the font daemon stopped answering and the run hung.

## SVG scale (2026-10-22, issue #13)

- **svg-scale — a size the file states is trusted; a size it only implies is asked about.** An SVG fixes its scale only with a viewBox and a physical unit (in, mm, cm, pt, pc) on its page width or height: Inkscape 1.x and CorelDRAW write that, and such a file imports at that size whatever scale is chosen. Anything else (Illustrator's `612px` Letter page, Inkscape 0.91's bare `744.09` A4, a hand-written file with no size) has user units whose length depends on the program: 72 per inch for Illustrator, 90 for Inkscape up to 0.91, 96 for the web and Inkscape 0.92 on. `SVGImporter.scaleGuess(of:)` is nil for a file that states its size, and otherwise gives the scale of the program that wrote it (Inkscape's `inkscape:version`, or the `<!-- Generator: Adobe Illustrator … -->` comment in the first 4 KB; a title or text that only mentions Illustrator does not count) or 96; `SVGImporter(pixelsPerInch:)` is nil to use that guess, or the user's choice. File ▸ Import of such a file opens `SVGScaleSheet` first (a queue like the 3D placement dialogs): the guess is selected, the drawing's size at each of 72, 90 and 96 is measured once and shown for the selected one, Cancel imports nothing. The importer also says what it assumed in its warnings, but only when nobody chose the scale, so in the app the sheet is where the user sees it (the warning serves callers without a dialog, and the tests). The scale is recorded in each shape's origin (`.imported(format: "svg", pixelsPerInch: 72)`; absent for a file that states its size, so those project files do not change) and shown in the inspector as "read at 72 px per inch": it is the scale the file was read at, not a statement about the shape's size after the user resizes it, and it does not say whether the scale was guessed or chosen.
- **Every length in the drawing follows the scale, not just the page.** The pixels of a unitless file are `1/scale` inch, so `SVGAttributes.pixels(_:percentOf:pixelsPerInch:)` converts a length with a physical unit (a page `210mm`, a `<rect width="1in">`, `font-size:12pt`, a `<use x="1in">`) against it: with no viewBox (or one that matches the page), the inch square is an inch whatever the scale, and the 90 px square is 90/scale inches. Without that, choosing 72 turned a 1 in rectangle into 1⅓ in. Inkscape 0.91 wrote `width="210mm"` with no viewBox and drew in 90-per-inch units; reading the page height at 96 would also have flipped every shape to the wrong place. A file that states its size is read at 96, where the CSS rule (an inch is 96 user units) is what its viewBox expects. The unit table is one dictionary, so `hasPhysicalUnit` and `pixels` cannot disagree (`50vmin` is not an inch size).
- **Clipart is not asked.** Inserting clipart has no dialog, so an SVG in the clipart folder that does not state its size is read at the scale of its program (a 1.33x change from before for an Illustrator file, 1.07x for Inkscape 0.91), and the guess is not reported there. That is the scale the file was drawn at, and `clipartWithNoPhysicalSizeIsReadAtItsProgramsScale` pins it; a clipart file that comes in wrong is corrected by importing it with File ▸ Import instead.
- **Not done.** Programs other than Illustrator and Inkscape (Sketch, Affinity) are not recognised, and an Illustrator file saved without its `Generator:` comment is not either: they are guessed at 96 and the sheet is how a user corrects them. An Inkscape 0.91 file re-saved by 0.92 with "ignore scaling" says 0.92 and is guessed at 96 for the same reason. The test fixtures are hand-written in the style of each program, not files saved by it.

## Save confirmation (2026-10-22, issue #10)

- **save-confirm — a save counts when the file holds the bytes of one of its saves, not when SwiftUI asks for the snapshot.** `KerfDocument.snapshot` used to set `lastSavedProject` at once, so `needsRecovery` went false and the recovery timer deleted the copy while the system was still (or never) writing: a read-only folder, a full disk or an unmounted volume left the work only in memory. SwiftUI's `ReferenceFileDocument` gives no callback after the write, so each `snapshot` now adds a pending save with an id (`KerfSnapshot.saveID`, carried through `fileWrapper` so encoded bytes are recorded against the save they belong to even if saves overlap), `fileData(for:)` records the size and SHA-256 of the bytes handed to the system, and `confirmSave()` hashes the file at `fileURL` and, when it matches a pending save (the newest that does), makes that save's project the saved one and remembers the file's digest. The file's content decides, so matched saves stay in the list. The recovery timer calls `confirmSave()` before its dirty check, which is the only consumer of the saved state, so there are no timers of its own. A failed or slow write never matches, so the document stays dirty and the recovery copy stays: the safe direction. The error the user sees is the system's own save-failure alert; Kerf adds nothing to it.
- **The file that matches nothing is "unknown", which is dirty.** The list keeps the last 8 saves, and a save can land late, after a newer one. So the last digest the file was seen with (`confirmedBytes`) is kept apart from the list, and `needsRecovery` is `savedStateUnknown || project != lastSavedProject`. `savedStateUnknown` is set when (a) bytes can reach the file that nothing can recognise any more: an encoded save is dropped from the list, a save is encoded after the list dropped it, or one save id is encoded twice with different bytes; or (b) at a tick, once any save has been handed over, the file is gone, unreadable, changing while it is read, of another size, or holds neither a known save nor the remembered digest (an older save that was forgotten landed over a newer one; something else replaced it). It is cleared when the file is next seen to hold a known save or exactly the remembered digest. Each of those was a way, found in review, for the document to look clean while the file held something else, and has a test: A written but unlooked-at then forgotten and undone to the original; an older save landing over a confirmed newer one, retained or already forgotten, and with a matching save in between; the file removed or replaced, before or after the first confirmation; a save encoded late or twice. Before the first confirmation the file might simply still hold the project as opened (every save failed), so an unmatched file there also keeps the copy: the safe side, settled by the next save that lands. Once a save is confirmed the remembered digest is compared on every tick for the rest of the document's life, which hashes the whole file each time (about 10 to 20 ms for a 20 MB project, on the main thread, once a minute by default). Confirmations are serialized by their own lock.
- **Not covered: other writers of the project's own file.** Only saves that go through `snapshot` are tracked. Save as Template writes a `.kerf` file the user chooses directly (`KerfDocument+IO`, `JobTemplateStore`), so choosing the open project's own path as the template destination, then undoing to the saved project, leaves `needsRecovery` false while the file holds the template; before the first tracked save there is no digest to notice it. That is a separate command with its own overwrite prompt and was not part of issue #10 (the same sequence behaved the same before); guarding it or routing it through the confirmation is not done.
- **What polling cannot close.** The file is only looked at on the recovery tick (once a minute by default; never if the interval is Off), because `ReferenceFileDocument` has no write callback. A stale write that lands between two ticks leaves up to one interval in which the document may look clean without a fresh copy, and a mismatch seen at the next tick keeps the copy from then on.
- **How the file is read.** Digests, not the bytes, are kept (a project with images is megabytes, times 8). The file is opened `O_NONBLOCK` and refused unless `fstat` says it is a regular file of a size one of the saves (or the remembered digest) had, so a pipe or device put in its place cannot block the recovery timer (tested with a FIFO) and a file of any other size is never read. It is read in 1 MB chunks and refused on a read error or if the bytes read are not the size seen. A hung or hostile network mount can still stall the open or the read on the main thread (`O_NONBLOCK` does not help there), and opening a not-yet-downloaded iCloud file may start the download; not done.
- **What it does not confirm.** A document with no `fileURL` (untitled, saved only to the autosave folder) never confirms, so its recovery copy stays until it is saved to a file or Kerf quits normally: safer than before, when an autosave deleted it. A file changed by another program between the write and the check is "unknown", so the copy is kept.

## Warnings in the toolpath form (2026-10-23, issue #24)

## Hole milling: slugs, pilot holes and the helix angle (2026-10-23, issue #12)

- **hole-mill-safety — three silent cases of `HoleMillOperation` now speak, and the helix is bounded.** (1) A through hole bored with a helix leaves the core the swept ring does not reach (diameter D - 2d for a hole D and a tool d; none when D <= 2d), which is a free slug once the cut reaches the material bottom: it can jam against the tool. (2) Thread mode assumes a pilot hole. Both depend on what the rest of the job does at that centre, which the generator (a function of one operation) cannot see, so they are judged where the whole project is, in the toolpath form (`OperationWarnings.holeMillProblems`): a slug wider than the tool (the threshold) in a through cut is reported unless an earlier enabled Drill at the centre goes through the material and is at least as wide as the slug (the drill-out; HoleMill has no tabs); a thread hole larger than the tool is reported when no earlier enabled toolpath in the list drills, bores (with no core) or pockets over the centre, to the thread's cut depth and at least as wide as the thread mill (a pocket counts by the room round the centre inside its vectors, a helical bore only when it leaves no core, i.e. a hole up to twice its tool; a profile cuts the perimeter only and a wider bore only a ring, so neither is a pilot). An earlier toolpath counts only if it starts at the top (its start depth is 0: one that starts lower leaves material for the tool to cut), a pocket by the area its tool can reach (the region shrunk by the tool's radius and allowance and grown back), and the copies of an array are holes at their offsets (and pilots at theirs, each copy that reaches the point judged by its own width), only toolpaths on the thread's own sheet and side count (the others are other programs), and a toolpath whose depth is not past its start depth cuts nothing. A toolpath that fails to generate for other reasons (a stepover of zero, say) is not second-guessed here: it shows its own error. A toolpath projected onto a 3D model is cut to depths only calculating knows: as a hole mill it says so ("cannot be judged from its settings: check it in the 3D preview") where a slug or a pilot could matter, and as an earlier toolpath it counts as no pilot. List order is what is judged, an operation not in the list has nothing before it (Group by tool can reorder the program). A thread that would take more than 10,000 turns is refused like a helix. (3) For holes barely larger than the tool the helix radius is tiny, so the pitch (default the tool's stepdown) made the descent almost vertical at the feed rate. The helix now descends no steeper than `HoleMillOperation.maxHelixAngle` (the default ramp angle, 10 degrees): where the pitch would be steeper it turns more often (the hole is then reported as "held to a 10 degree ramp", about holes less than roughly 0.22 in larger than a 1/4 in tool at a 0.125 in pitch); where the limit is what asks for more than 50 turns (a pitch the user chose that is already gentle stays a helix however many turns it takes), or the hole is the size of the tool, there is no helix and the hole is peck-drilled at its centre (pecks of the helix pitch, retracting to safe Z between them, with a lap at the hole's own radius at the bottom of each peck so the hole comes out its size; reported as "peck-drilled instead"; the old straight single plunge for a hole the size of the tool is replaced by the same pecks). A thread hole as large as the tool, which was skipped without a word, is reported. A helix needing more than 10,000 turns (a huge depth at a pitch the tolerance floors, 0.001 in) is refused with a message instead of being spread over fewer turns, which would break the angle limit; an infinite depth and a helix pitch that is not a positive number are refused too. Roomy holes (the 10-degree limit is not reached) produce exactly the program they did. The tool's own ramp angle does not exist (tools have no such field), so the ramp default is the limit; a per-toolpath setting can be added if someone needs another angle. Tests: `Ops2DHoleMillTests` (no helix steeper than the angle for holes 0.06 to 0.5 in larger in both Z-zero modes, the peck fallback for 0.01 in and 0 in larger with its retracts, roomy holes unchanged, the thread warning) and `OperationWarningsTests` (the slug and pilot cases, one assertion per rule and each way to satisfy or defeat it).

## Facing (2026-10-23, issue #20)

- **facing — a rectangle faced by a raster or a spiral of the tool's center, led in from outside.** `OperationKind.facing` (`FacingOperation`, `FacingParameters`) takes a layer off the top of an area: the whole material (the default with nothing selected) or the bounding box of the selected vectors. The tool's center covers the area grown by `overhang − tool radius` on every side; `overhang` is how far the *cutter's edge* reaches past the area's edge and defaults to the tool radius, so the center rides the edge and the edge comes out clean (a smaller overhang leaves the corners rounded, which the form says; under zero is refused). Patterns: `rasterX` and `rasterY` (passes alternate direction, joined at the ends, `stepover` apart at most) and a `spiral` of rectangular rings from the outside in (climb is clockwise, with the stock still to be cut on the tool's right; rasters alternate, so half their passes are climb whatever `direction` says and the form only shows it for the spiral), each ring started at its corner and linked to the next by a diagonal (rings are kept at most 85% of the tool diameter apart whatever the stepover: at an outside corner of the inner ring the round cutter leaves a spot 0.586 × the spacing from the nearest cut, which passes a radius at 85.4%; the program says when it held them, rasters go to 95%), with one last pass down the middle when the rings leave a core wider than the tool (the rings' last square is under two steps wide, which a cutter-width core can survive). Stepover is a fraction of the tool diameter (default 0.7, at most 0.95 so the passes overlap), not the tool's own stepover field: a surfacing bit is run wide and the tool library's value is tuned for pockets. The first pass is led in: the plunge is at least one tool radius before the first cut and as far as it takes for the center to be a tool radius outside the area (so the cutter touches none of it, whatever the overhang: with an overhang under a radius the first cut itself is inside the area), and a raster's last cut runs out the same way before the retract (a spiral ends in the middle of the faced floor and lifts there), so the first contact with the surface is a feed, not a plunge. Depth passes are the usual `DepthSettings` (a layer is 1/16 in by default, passes by the tool's stepdown); each layer repeats the same pattern and re-enters at the lead-in with the previous floor credited, as pockets do. Not done: a one-way raster (rapid back each pass), a ramp lead for an area inside the stock (the plunge there is in stock beside the area), and a surfacing-bit tool kind: any end mill is a facing tool and a new facing picks the widest one in the library. A facing of the whole material has no vectors, so like a 3D relief it belongs to the first sheet and the top side (`sheetID(of:)`, `side(of:)`); in a document with other sheets or two-sided machining the form says so and points to a rectangle on the other sheet or side with Selected vectors. Safety: the cutter reaching past a selected area into surrounding stock is a form warning ("not being faced"), computed from the cutter's reach (the area grown by a radius plus the larger of the overhang and a radius, which bounds the cutter's edge at the overhang and at the lead-in's far end for every pattern; clipped to the material) against the area clipped to the material, so facing the whole material, where the overhang is air, never warns. The program is the usual single toolpath (Z through the Z-zero helper, both modes tested). Facing changes where the top of the material is for the steps after it, and the program still measures every later depth from the original top (or the spoilboard): the result's `note` (inspector and job sheet) says how deep the new surface is and, with Z0 on the top, not to re-zero after the step. Tests: `Ops2DFacingTests` (coverage of every sampled point within a tool radius of the path, for the three patterns and sizes from wider than the tool to narrower, including the spiral's core, in both Z-zero modes; passes along the chosen axis alternating at no more than the stepover; plunge and last cut clear of the stock; spiral direction; layers; overhang; warnings; refusals; saving). `samples/faced-board.kerf` and `.tap` (a 12 x 8 in board faced 1/32 in, then a plaque cut out) are checked by `SampleFilesTests`, which regenerates the program.

## Command line export (2026-10-23, issue #17)

- **kerf-cli — a second product of the app's target, not a library split.** The export path (`GCodeExporter`, `ToolpathCalculator`, the two-sided project logic, the stores for posts and machines) lives in `KerfApp`, an executable target, which no other target can import. Moving it to a library meant making a few dozen internal types and functions public and giving every test that uses them a second import; the issue allowed that only "if it proves heavy", and it is. Instead `Package.swift` declares `.executable(name: "kerf-cli", targets: ["KerfApp"])` beside `Kerf`, and `main.swift` (which replaced `@main` on `KerfApp`) asks `KerfCLI.runIfRequested` first: a binary called `kerf-cli` is always the command line, and `Kerf` is only for a first argument that is a command name (`export`, `posts`, `help`), so Finder's own arguments and a path to open still start the app. The command line therefore links AppKit and SwiftUI like the app but never starts either (no `NSApplication`, no window server). The one shared function that moved is `KerfProject.exportProject(for:side:)` (what `KerfDocument.outputProject(for:)` did), so the sheet and the command line cannot drift apart on which sheet, side or job a toolpath is posted with.
- **Same bytes as the Export sheet.** The command line follows `ExportGCodeSheet.post`: it calculates the toolpaths that are exported (enabled ones, or the named one) against the whole project, collects them with `GCodeExporter.toolpaths`, adds the post-not-installed and missing-toolpath errors, and posts with the project's post (or `--post`) with the project's machine applied. The job name in the header is the project's document name, as in the app (`Untitled` for the samples; `--name` overrides it, and `samples/sign.tap` is the same program under `--name Sign`); the file name is the project file's base name (plus `_<toolpath>`). Tests compare the file with the app path in-process (`KerfDocument.calculateNow` then `GCodeExporter.export`) for the whole program and for one toolpath. It never reads the user's tool library: tools come from the project's own snapshot and the seeded defaults, so the result does not depend on whose Mac it runs on; posts and machines in Application Support are used unless `--builtin-only` (which the CI check passes).
- **Exit status.** 0 = a program was produced and the validator found no errors (warnings are printed to standard error and do not fail the run: the sample ships clean, but a warning is for the operator's eyes, not a build breaker); 1 = validator errors, or nothing to export (a calculation that failed counts, as the sheet's "missing from the program"); 2 = a usage error, an unreadable or invalid project, an unknown post or toolpath name, or a failed write. With errors nothing is written unless `--force`, which still exits 1: the Export sheet's "Save Anyway" needs a confirmation and a script has none to give, so the default is to not leave a program with errors in the output folder. A post id that is not installed is an error to settle (the sheet's "Pick a post before saving"), and naming an installed one with `--post` settles it: the sheet keeps reporting it after another post is picked until the file is saved, which has no counterpart on a command line. A toolpath that did not calculate stops the run even with `--force` (a step missing from the program); `--force` is for the validator's errors and the not-installed post. A toolpath name is matched exactly first and then without regard to case; two toolpaths with one name must be told apart by renaming. `--side` picks the side of a two-sided job for the whole program (default top; the app's shown side), and a toolpath asked for by name is posted with its own sheet and side whatever `--side` says, as the sheet posts a single toolpath (`exportProject(for:side:)`); `--group-by-tool` is the sheet's option (off by default, as in the app).
- **CI and drift.** `scripts/check-samples.sh` builds the product, posts every `samples/*.kerf` with every built-in post (`kerf-cli posts --builtin-only`) and diffs the programs against `samples/expected/<post id>/<sample>.<ext>` (`--update` rewrites them; a sample that does not post cleanly fails either way). `.github/workflows/samples.yml` runs it on `macos-15` for pull requests and main. The same comparison is a test (`KerfCLITests.everySampleWithEveryBuiltInPostIsTheCommittedProgram`), so `scripts/test.sh` is the guard locally and the workflow is the guard for a change nobody tested. Not done: other file formats in `samples/` (the DXF and STL are import fixtures, not projects), a `--all-posts` flag (the script loops), and exporting each tool or each operation to a file of its own (the sheet's batch export).

## Heavy SVG imports (2026-10-23, issue #30)

- **heavy-svg — the cost was the canvas, not the import; the import stays on the main thread.** Timed with generated traced-style SVGs (closed paths of cubic curves with wobbling control points, in groups): 5,000 paths of 100 curves each (22 MB, 500,000 segments) parse in 0.23 s in a release build (1.5 s debug), `ImportService.importFile` adds the shapes in 0.2 s, and the near-miss report (`ImportGaps`) takes 17 ms at 8,000 paths (it grows with the square of the path count, but 100,000 paths would still be about 2 s; not changed). Drawing the result took 15 s, once per redraw, in release and debug alike, because the cost is CoreGraphics': a stroke exactly one point wide has a fast path and any other (the canvas used 1.25 points, round joins and caps, and a dashed second stroke over a selected shape) goes through the full stroker at about 30 microseconds a curve segment, and an import leaves every new shape selected, so every later redraw paid it. A progress sheet for the parse would have bought nothing. Fixed in two places: (1) `CanvasDetail`: a drawing of more than 5,000 segments (the full stroker draws that in about a tenth of a second) is drawn as hairlines, one point wide with the default join and cap, one color per shape (the layer's; the selection color for a selected shape, with no dashed copy; locked shapes at 45% as before), shapes whose box cannot reach the view are skipped, and the state is set once for all of them. The same 500,000 segments draw in 0.24 s unselected and under a second selected in a debug build; 8,000 small paths selected went from 7.3 s to 0.29 s. A drawing under the threshold looks and draws exactly as before. (2) Looking shapes up by id was a scan of the document per id, so `selectedShapes` (called by the transform handles on every redraw), grouping, `expandToGroups` and ungrouping cost the square of the selection: `Document.shapes(ids:)` indexes the document for more than 16 ids, `expandToGroups` indexes the groups and expands each once (a selection inside one huge group was a pass per member), and `ungroup`/`ungroupAllLevels` and `DesignCommands.group` use `shapes(ids:)`. 40,000 shapes selected, expanded and ungrouped take milliseconds; the same results as the scan are pinned for random documents with repeated ids, unknown ids and groups. Not done: the toolpath overlay still strokes at 1.5 to 2.5 points with round joins (a heavy toolpath draws as slowly as heavy shapes did), the canvas redraws everything on each mouse move rather than keeping an image of the still drawing, `project.bounds(of:)` flattens every selected shape on each redraw (0.12 s for 8,000 shapes in debug), and `ImportGaps` stays quadratic. Tests: `CanvasDetailTests` (threshold, visibility, a 150,000-segment drawing is drawn as hairlines selected or not and a light one is not: the draws are counted, because how long a draw takes depends on what else the machine is doing (it took 0.5 to 0.7 s alone and 17 s once beside the CAM tests), shapes out of view change no pixel, the selection color) and `DocumentLookupTests`.
- **vcarve-parity — start depth and the flared wall (issue #96).** Carving from a start depth S leaves the V-bit's cone widening above S, so a V wall reaches the surface S · tan(half angle) outside the vector, and a tapered tool with a wider cone than the V-bit (tT > tV) is closest to it there. A tapered flat-area clearance tool's wall clearance is therefore its tip radius + (S + flat depth) · max(0, tT − tV), and corner sharpening lifts the tool to ((R − tip radius) − S · max(0, tT − tV)) / max(tT, tV) below S; the two earlier vcarve-parity entries measured both from S. Nothing changes when S = 0 or the tool's cone is no wider than the V-bit's. The V-bit's own tip radius is still not subtracted from the clearance, which errs on the safe side.
- **keep-out — the export check tests every piece exactly (issue #96).** `KeepOut.violations` used to sample each move every 0.9 R (R = tool radius + margin) and test the samples against the zone grown by R. A move grazing a convex corner crosses the grown region along a chord of 2 · sqrt(R² − h²), which is shorter than that step once the tool radius passes about 0.42 in (8.4 mm), so a cutter overlapping a clamp could pass between two samples. Each straight piece (an arc is cut into chords within the geometry tolerance) is now cut where it crosses the grown outline and where it passes the zone top, and the middle of each part is tested, as `KeepOutAvoidance` already did when it re-routes a move.
- **thread-mill hand (issue #96).** Climb or conventional is how the cutter meets the bore wall and depends on the direction around the bore alone (counter-clockwise is climb with a clockwise spindle); the hand of the thread depends on that direction together with the direction along Z (counter-clockwise while rising, or clockwise while descending, is right-handed). Left-hand threads used to flip the rotation and keep climb going up, which made a requested climb cut conventional and the reverse. The rotation now follows climb/conventional and the hand sets up or down: right-hand climb goes up, right-hand conventional comes down, left-hand climb comes down, left-hand conventional goes up. Right-hand output is unchanged.
- **chamfer — tip clearance applies only beside the line (issue #96).** A chamfer "On" the line puts the tip on the vector, so its tip clearance is taken as 0: it used to size the cut for a tip `clearance` off the edge (a bevel `clearance` wider on each side and `clearance / tan(half angle)` too deep) that the profile never produced. Outside and Inside are unchanged, and the Tip clearance field is hidden for On.
- **ramps — the smooth ramp keeps its maximum angle on a short loop (issue #96).** The smooth ramp is `drop / tan(max angle)` long at least, but used to stop at one lap, so a loop shorter than that (the inside of a 1/2 in hole with a 1/4 in mill is 0.785 in round) went down at 17.7° for a 0.25 in pass with a 10° limit. The length the user asked for is still cut short at one lap; the angle limit is not: the ramp goes round again (a helix, at most 200 laps) and then cuts one whole lap at the pass depth. Loops long enough for the ramp are unchanged. The spiral ramp (one lap whatever the drop) is still unbounded.
- **tiling — the largest tile includes the overlap (issue #96).** `ToolpathTiling.cells` counted tiles from the job size and the largest tile alone, then grew every tile by half the overlap on each shared edge, so tiles were wider than the machine's reach (a 120 in job on a 60 in machine with 1 in overlap made 60.5 in tiles) and the export refused them with a travel error. The count now leaves room: n tiles of extent / n, widest extent / 2 + overlap / 2 for two tiles and extent / n + overlap from three. With no overlap the grid is the same as before. An overlap of half a tile or more is ignored, on that axis and in the tile regions as well as the count (the sheet says so): the count grows as extent / (tile − overlap), so 59.99 in of overlap on 60 in tiles asked for 12,000 tiles an axis, posted again on every keystroke in the field. Below half a tile a grid is at most about twice the size it is without overlap. The same 120 in job with 1 in overlap now needs three tiles.
- **cad-io — the DXF spline tolerance is a length in the document's units (issue #96).** `DXFImporter.splineTolerance` (0.001) was applied in the file's own units, so a metre or foot drawing was sampled thousands of times more coarsely than a millimetre one (a 100 mm quarter circle: 14 samples and 0.17 mm between them in metres, 200 and 0.001 mm in millimetres). It is converted per entity, over the whole entity-to-document transform (file units and any INSERT scale, rotation and mirror, by its largest stretch), so a magnified block is sampled finer (up to the 200 samples a span the sampler has always been limited to, which a magnification of about 100 on a 10 mm curve reaches). Entities that are not magnified, in files in the document's units, are sampled as before; a millimetre file in an inch document is sampled at 0.001 in rather than 0.001 mm.
- **cad-io — SVG percentage lengths on shapes resolve against the viewport (issue #96).** Percentages used to resolve against 0, so `<rect width="50%">` was dropped without a word and a percentage position landed at 0. The reference is the viewBox (else the root's width and height in pixels): x, width, cx, rx, x1, x2 and dx against its width, y, height, cy, ry, y1, y2 and dy against its height, r against sqrt((w² + h²) / 2), as in the SVG spec. A file with neither viewBox nor a size still reads percentages as 0. Nested `<svg>` viewports are not tracked.
- **cad-io — an SVG with no viewBox and no height rests on the bottom edge (issue #96).** The page height was taken as 0, so flipping Y about it put every shape at negative Y, off the material. When neither a viewBox nor a height (in a unit that is not a percentage) is given, the lowest point of the imported content is the bottom of the page; shapes, sizes and X are untouched and their relative positions are kept. Embedded pictures count towards the bottom as well as shapes, and the import warns that the artwork was placed on the bottom edge. Files that give a height are not moved.

## Release pipeline (2026-10-23)

- **one-assembler — `scripts/bundle.sh` builds every bundle, local or release, and the workflow only orchestrates.** It takes `LOFTLINE_VERSION` (numeric, no `v`), `LOFTLINE_CHANNEL` (`dev`, `rehearsal` or `release`) and `LOFTLINE_SIGN_IDENTITY` (default `-`, ad hoc), writes the version and a `LoftLineChannel` key to Info.plist, and copies `packaging/updater/macos.sh` into `Contents/Resources/updater.sh` before signing, because the signature and notarisation cover the whole bundle. A bad setting (an unknown channel, a version that is not `X.Y.Z`, a release without a version) is refused before the build starts. `scripts/check-bundle.sh` builds it the ways the release does and checks the plist, the helper, the signature and the extension's entitlement, then runs the smoke test on the real binary. The logic that decides whether a build may ship is in small scripts with tests (`check-test-run.sh`, `release-smoke.sh`, `check-bundle.sh`, `check-release-workflow.sh`), not in YAML.
- **inside-out-signing — the Quick Look extension is signed first with its own entitlements, then the app, and `--deep` is never used to sign.** Both reference workflows sign with `--deep`, which re-signs the nested extension without its entitlements and breaks its sandbox. With a real identity `bundle.sh` adds `--options runtime --timestamp`; `check-bundle.sh` records the `codesign` calls through a stub (extension first, app second, no `--deep`) and checks the real ad-hoc bundle still shows `com.apple.security.app-sandbox` on the extension, and `release.yml` checks the same plus the hardened-runtime flag on the signed one. The app has no entitlements file yet. The hardened runtime may break the JavaScriptCore JIT (gadgets) or the runtime Metal shader compile, and only the rehearsal's checklist shows it; if so `Resources/LoftLine.entitlements` gets only the entitlement that failure proves necessary, and `bundle.sh` already passes it when the file exists and the identity is real.
- **rehearsal-channel — only a tag push is a release; a dispatch run is a rehearsal with a numeric version.** The dispatch input `version` defaults to `0.0.0`, so a run from `main` can never stamp a branch name into a bundle or produce one that thinks it is a release. The rule reads the event as well as the ref: a dispatch run pointed at a tag is still a rehearsal and creates nothing. A tag must match `^v[0-9]+\.[0-9]+\.[0-9]+$` or the job fails (the trigger `v*` also matches `v1.2.3-rc1`). Rehearsals keep the zip as a workflow artifact for 7 days; without the signing secrets they still build, test and smoke-test an ad-hoc bundle and skip signing and notarisation.
- **gate-by-line — a release is gated on the test result lines and a minimum count, never on the exit code.** `scripts/check-test-run.sh <log> <min> [<targets>]` passes only if there is at least one `Test run with N tests [in S suites] passed` line (older Swift Testing, such as the macos-15 runner's Xcode 16.4, prints no suite clause), every such line says passed, the counts add up to the minimum, and exactly one line printed per test target: the workflow passes the number of `.testTarget(` entries in `Package.swift`. The total alone cannot see a missing small target (without CGeom's 6 tests the total is still above 1450). A toolchain that runs every target in one process prints ONE combined line, which is accepted: Xcode 16.4 on the macos-15 runner does (run 40538185730 printed `Test run with 1514 tests passed` once, where a newer toolchain prints five lines). A single line cannot be one target's, because the minimum is above the largest target's 724 tests, so keep it there. The per-target count is therefore only enforced on a toolchain that prints per target; the earlier "exactly one line per target" claim was true of the development Mac and was never observed on the runner. `LOFTLINE_MIN_TESTS` is 1550 (the suite is about 1,600 tests and the largest target has 772). The workflow runs `scripts/test.sh` with `set +e`, logs the exit code without using it, then runs `scripts/check-samples.sh` without `--update`. The smoke test runs the bundled, notarised executable on the sample sign and requires byte-identical G-code, so the hardened runtime is proven not to change output. The full suite has never run on a hosted runner before the first rehearsal; a test that needs a window server or Metal could fail there.
- **draft-first — a tag run only creates or fills a draft release, and never touches a published one.** A draft is never "latest", so no installed app can be offered a release whose update feed does not exist yet; the feed job and the step that publishes the draft come with the updater. A tag whose release is already published fails the job instead of uploading, because `--clobber` deletes an asset before replacing it, so a fix ships as a new tag. `scripts/check-release-state.sh` says whether a tag may be uploaded to (`absent` or `draft`; a published release or an unreadable answer exits 1) and runs twice, when the run starts and again just before the upload, because a draft can be published while the build runs; what is left is the instant between that check and the upload. A concurrency group per ref queues two runs for one tag. `scripts/configure-release-ci.sh` is a copy of rootkit-game's setup script that refuses to use any `rootkit` repo, creates a separate private vault, refuses a `VAULT` or `ASC_KEY_ID` that `release.yml` does not use (it reads both from the workflow, so a setup can never provision something CI will not ask for) and a p12 whose certificate is not the expected identity (the login keychain also holds another team's Developer ID item), makes a new read-only deploy key on every run (the original reused an old key that no longer matched its secret), retires the previous key only after the new secret is set, and passes passphrases and secrets through the environment and stdin, not argv.
- **updater-handoff — closed in the updater plan (see `updater-binding`): the helper installed a path, not the verified archive.** The app verifies the SHA-256 and signature while downloading, but may install on quit, and `macos.sh` takes only `--archive <zip>`; its `codesign --verify` proves a valid signature, not that the bytes are the ones the app approved or that the team is ours. Before the first release, the helper should take the digest the app verified (`--sha256`), check the staged copy against it and extract that same copy, and require the Team ID in its codesign requirement; the app should also re-verify just before spawning it. The helper installed in a release does the next update, so this has to be settled before `v0.2.0`.
- **secrets-scope — the signing secrets are repository secrets.** Anyone with write access can read them by pushing a branch with a workflow that prints them (a repository-level trust boundary, not something `release.yml` can prevent). The repository has one writer today. If a collaborator is ever added, move the secrets into a GitHub Environment limited to `main` and `v*` tags and protect `main`; both are repository settings.
- **hosted-runner-renders — the Help render is sampled more finely on a GitHub runner.** The first rehearsal (run 40529280132) failed the gate on `utilityWindowsRender`: on the macOS 15 runner an offscreen Help window draws only its search field, 2 distinct colours at the default sampling against 52 on a development Mac (probe run 40534368182; the runner's image is `Tests/Fixtures/LoftLineApp/hosted-runner-help-render.png`). A window that is never displayed does not realise its sidebar list or topic text there. On a runner (`GITHUB_ACTIONS=true`) the Help render is sampled at a step of 7 with the same minimum of 4 colours, which still scores a flat image 1; on a development Mac it keeps the default sampling and must show the sidebar and the topic. The other render tests drew enough on the runner. Cost: a Help window that lost its list or text would pass on the runner and be caught only by the local run (AGENTS.md requires a green local suite before a merge). A displayed Help window on macOS 14 or 15 has not been looked at.

## Updates (2026-10-23)

- **updater-pattern — rootkit-game's signed feed, ported; not Sparkle.** A static `latest.json` on the release, an RSA-4096 signature over the archive, a small install helper started when the app quits. Sparkle's strengths (one-click UI, delta updates) cost a binary framework in a bundle assembled by hand under a Command-Line-Tools-only toolchain and its own nested signing; the spec's Alternatives table has the rest. `UpdateCore` has no AppKit, so the parsing and verification are unit-tested without a window. Revisit Sparkle if delta updates are ever wanted.
- **feed-signature — what is signed and how it is checked.** The signature is `openssl dgst -sha256 -sign key -binary < archive`, checked in Swift with `SecKeyVerifySignature` and `.rsaSignatureDigestPKCS1v15SHA256` over a streamed SHA-256, and in `scripts/verify-feed.sh` with openssl; a test makes both accept the same feed. The public key is a PKCS#1 `RSA PUBLIC KEY` (what `SecKeyCreateWithData` takes), committed twice, in `Sources/UpdateCore/UpdatePublicKey.swift` and `packaging/updater/update-public-key.pub`, with a test that keeps them equal; it is a NEW keypair and rootkit-game's is never reused. The private key stays in `~/.config/loftline/update_sign.key` and the secret `UPDATE_SIGN_KEY`; `genkey` prints only the public key, so no secret reaches a terminal. `genkey` was run on 2026-10-27 and the committed public key is its output. Until then the committed key was a placeholder whose private half was never written anywhere, which failed safe (nothing could verify against it), and a test now keeps that placeholder from coming back. The private half is in `~/.config/loftline/update_sign.key`; the Actions secret `UPDATE_SIGN_KEY` is set by the owner, and a tag run refuses to start without it. `notes`, `gcodeChanged` and `gcodeChangedIn` are not signed (TLS only). `gcodeChangedIn` is the newest release, up to this one, whose posted programs or golden fixtures differ from the release before it, computed from the tags in version order: `gcodeChanged` alone compares only adjacent releases and says nothing to someone who skips one (0.2.0 straight to 0.2.3 passes a change made in 0.2.1), so the app warns when `gcodeChangedIn` is newer than the installed version and falls back to the flag when the field is absent. `scripts/verify-feed.sh` enforces the client's manifest contract as well as the digest and signature (url equal to the asset's download URL, version matching the archive name, notes and gcodeChanged types, gcodeChangedIn not newer than the release, document size), because it gates publishing and a feed a client refuses would leave every installed app unable to update. Rotation: the key is baked into every shipped app, so a key that must change (not one that is compromised) ships as a release signed with the OLD key whose app carries the NEW key; the release after it is signed with the new key. A compromised key cannot be rotated away from inside the app, and the installed base would have to reinstall by hand. That is the cost of an updater with no revocation channel, and it is accepted. The manifest parser refuses rather than clamps: only `https://github.com/seanperkins/loftline/releases/download/<tag>/<asset>` URLs of safe characters (no dot segments, query or credentials), a version that starts with a digit and holds only version characters (it names the cached file), a signature of exactly 512 bytes, a document under 256 KiB. Test keys are generated at test time, never committed.
- **updater-binding — the install is bound to the bytes the app verified, and to our team.** (Closes `updater-handoff`, issue #118.) The app hands the helper the SHA-256 it verified (`--sha256`, required). The helper copies the archive into a private folder, hashes that copy against the digest, unpacks that same copy, and requires the unpacked app to satisfy a codesign requirement: our bundle identifier, a Developer ID Application certificate and our Team ID. `codesign --verify` alone says only that SOME signature is intact, so another app signed by the same team and renamed `LoftLine.app` would otherwise be installed. The app also re-hashes the cached archive in `applicationWillTerminate` just before it starts the helper, and starts it with a fixed minimal environment so the helper's test-only switches (`LOFTLINE_UPDATER_*`) cannot be set from the app's. The real Developer ID requirement cannot be satisfied in tests (no such certificate), so the mechanism is tested both ways with an identifier requirement on an ad-hoc bundle, the requirement string is proved to PARSE against codesign (a malformed one exits 1 with a syntax error, a well-formed one that does not match exits 3), and the release workflow's Verify the signature step runs the real string, printed by `macos.sh --print-requirement` so there is one copy, against every notarised build with `codesign --verify -R=`: a typo fails the release, not every install in the field. The helper also takes `--version` (the version the user was offered) and refuses unless the unpacked bundle, which is what the signature covers, is that version AND newer than the installed app: a feed can claim any version, and an older validly signed release replayed as an update, or a download that waited while a newer version was installed by hand, is refused. The helper's output goes to `~/Library/Caches/LoftLine/Updates/updater.log` (it runs after the app has quit, so that is the only record of why an update did not happen), and its temp copy removes itself. Not done: a lock so two helpers cannot interleave (issue #117, low priority: the app starts one per quit).
- **install-timing — the helper starts only once quit cannot be cancelled.** `UpdateController` sets the install pending and `applicationWillTerminate` is the only caller of the helper, so cancelling a quit at a save prompt leaves the verified archive waiting for the real quit. The helper waits for the app's PID and aborts, swapping nothing, if it is still alive at the timeout. The swap is two renames, not an atomic exchange: a crash between them leaves no app and `LoftLine.old-<pid>`, and `macos.sh --recover` puts it back. The new app removes `LoftLine.old-<digits>` beside itself 20 seconds after launch, and only that exact shape. A translocated copy, an unwritable folder or a bundle not named exactly `LoftLine.app` refuses to install, with a message: the helper installs to `LoftLine.app` beside the running app, so updating `LoftLine copy.app` would leave it untouched and replace a different copy. The automatic check is throttled to once a day with five minutes of slack, because the daily timer starts when the launch check starts and that check ends a few seconds later, so without slack every other tick fell a few seconds short and a session left open checked every 48 hours.
- **publish-after-verify — a release is published by the feed job, and only after its feed verifies.** The build job leaves a DRAFT. The feed job (`needs: build`, tag pushes only, never a dispatch on a tag ref) checks the release is still a draft, signs the feed, uploads `latest.json` to the draft, downloads the zip and the feed again from the draft, runs `scripts/verify-feed.sh` on those downloaded files, checks the draft state once more and only then runs `gh release edit --draft=false`. A failure anywhere leaves a draft, which no installed app can see. A missing `UPDATE_SIGN_KEY` stops the build job at its start, not after a notarised draft exists. `scripts/check-release-workflow.sh` pins the order and the guards, and was mutation-tested.
- **dev-never-updates — which builds ask.** Only the `release` channel checks by itself, at launch and then daily (never more than once a day), and only with the preference on. A `dev` build can be asked by hand, says it does not update, and may be pointed at a test feed with `LOFTLINE_UPDATE_FEED_URL`, honoured on `dev` only; a `rehearsal` build never checks. A dev build never installs. `LOFTLINE_NO_UPDATE_CHECK=1` silences every check (tests, the UI harness, CI). A skipped version is hidden from background checks but a manual check still shows it.
- **updater-proof — open.** The updater is proven only when an installed 0.2.0 finds, downloads, verifies, replaces itself with and relaunches as 0.2.1 with no `LoftLine.old-*` left, and the tamper drill in TESTING.md refuses a wrong digest. Recorded here when those have run. Unverified until a real draft exists: that `gh release view/download/edit <tag>` can find a DRAFT by its tag (the by-tag REST endpoint hides drafts). Two reviewers recalled that gh's `FetchRelease` looks drafts up through GraphQL first, and the installed gh has that function, but nobody has run it against a draft here. A failure leaves only drafts, invisible to every installed app, but a re-run would then create a second draft; prove it with one scratch draft before the first tag.
- **updater-trust-boundary — what the update path trusts, and what it does not (final review of the updater plan).** The signature covers the archive, not the feed's fields, and the build and feed jobs hand the zip over through a mutable draft release. Both were raised as findings and both stay, for one reason: whoever can edit a draft release or `latest.json` in this repository can already read the signing secrets by pushing a workflow (`secrets-scope`), so signing the manifest, or passing a digest from the build job to the feed job, would defend against nobody who is not already trusted, and signing the manifest would also pin every installed app to a feed format. What bounds a bad feed is the helper: it installs only a bundle with our bundle identifier, signed by a Developer ID certificate of our team, whose own version is the version offered and is newer than the one installed, from bytes that match the digest the app verified. A feed edit can therefore not install an older or foreign build; it can only withhold an update, or hide the post-output warning. If a collaborator is ever added, revisit `secrets-scope` first. Also not done, and left to a later change: a byte limit while the archive downloads (it is checked afterwards, so a hostile server could fill the temp folder first), a way to cancel an install-on-quit that is pending, and a digest handoff between the build and feed jobs.
- **release-retries — Apple's servers drop connections, so the steps that call them are retried.** The first `v0.2.0` run (2026-10-27) died in `xcrun stapler validate` with `NSURLErrorDomain -1005 The network connection was lost` to Apple's CloudKit, after notarisation was Accepted and the staple had worked; both rehearsals had passed the same step. Nothing was published, because a release is only created after the build. Stapling and its validation now go through `scripts/retry.sh 4 15` (up to four tries, 15 s, 30 s, 45 s apart; the command's own exit status comes back after the last, and each retry is printed). `notarytool submit` is sent again, up to three times, only when it came back with no status at all, a transport failure; an `Invalid` answer is Apple's verdict and is never retried. `scripts/check-release-workflow.sh` pins both and was mutation-tested. Not retried: `gh` calls and the build itself, because a failure there is a real failure or a draft that is simply re-run. A re-run of a run uses the workflow file at the TAGGED commit, so a fix to the workflow reaches a release only if the tag is on a commit that has it; for a tag that never produced a release, the tag is moved.


## Projects carry their post, machine and tools (2026-10-27)

- **project-carries-post — a `.loftline` file holds a full copy of its post and machine, and the file's copy posts.** The same file used to post different G-code on two Macs (the post is looked up by id, and a missing one fell back to the default, which can be another dialect). Format version 2 adds `postSnapshot`, `machineSnapshot` and, for a project with no chosen machine, `machineInferredFor`. The copies are plain `JSONValue` because CAMCore cannot name PostCore types (PostCore depends on CAMCore); `ProjectPost` in the app layer reads them back. The copy wins while its id still equals the selection; the installed definition is used to compare, and when the user picks something else. A difference is a warning (Job Setup, the export sheets, Save All, tiled export) with an **Update This Project** button, never a silent change. A nil `postProfileID` / `machineID` is never written by attaching: nil keeps meaning "the default for the units" and "inferred from the post", so an old project that switches posts or converts units resolves exactly as before; the marker `machineInferredFor` is what makes a machine copy for a nil id decidable from the file alone. Hand-built test projects stay copy-less on purpose. Opening a version 1 file attaches the copies in memory only and leaves the document unedited.
- **snapshot-schema — a copy this LoftLine cannot read is refused, never read with fields dropped.** `JSONDecoder` ignores keys it does not know, so a post that gains a field in a later LoftLine would silently post different G-code in this one. `PostProfile` and `MachineDefinition` carry `schemaVersion` (1; absent decodes as 1), a newer one throws `SnapshotError.newerSchema` before anything else is decoded, and every place a file becomes a project that can be posted goes through `LoftLineProject.opening(from:)`: document open, recovery, templates, the harness and `loftline-cli`. A copy that is damaged, or present but `null` (synthesized `Codable` reads that as absent, so it is checked on the raw object), is refused with the same kind of message. User post and machine files with a newer schema are skipped like unreadable ones. An older LoftLine refuses a version 2 file by its format version. Part 3 (the post editor) will tell the user about a skipped file.
- **tool-copy-wins — tools follow the same rule.** Before, `mergedTools` let a library tool win over the project's tool of the same id, and every save overwrote the file's tools from the local library; `loftline-cli` already posted from the file's tools, so the app and the CLI could disagree for one file. Now the project's tool wins; the project carries every tool its operations use (`ToolSync.carrying`, after every edit, live edit and open); a save no longer overwrites; a template's tool wins when it is applied (a clash with a different carried tool gets a fresh id and the added toolpaths follow it). A Tool Database edit still reaches an open project through `ToolSync.applyingLibraryChange`, as one undoable step, only when the carried copy equalled the library's old entry, so a rename in the library cannot swap the diameter of a copy that had diverged, and the carried notes and group are kept. A tool is compared on everything except notes and group (the name is written into the tool-change comment). Staleness follows `cutsSameToolpaths`: a rename never makes toolpaths stale. Alongside: `calculateUntilFresh` makes every sheet that calculates then posts or validates recalculate a result that landed after a later change, because a stale result was being posted (machine output) once the project could change while it calculated.
- **review-outcomes — what the final review changed (2026-10-27).** A copy with no installed counterpart is now a warning at export, not only a line in Job Setup: a project's post or machine can come from a file someone else made, and its lines and bed limits are then the file's alone. A project with no chosen machine records "none found" (`machineInferredFor` with no machine copy), so a custom post keeps its own limits on a Mac that happens to have a machine listing it. A post may ask for 0 to 12 decimals (a larger number would exhaust memory at export), checked wherever a post is read. The post pickers list a carried post that is not installed here. The export sheets drop the project's own post's notices when the program is posted with a post the user picked, as `--post` does.

## Coolant and park-and-probe tool changes (2026-10-27)

- **coolant — per toolpath, applied when posted.** `OperationSetup.coolant` (nil = Off, so every older file reads as Off) is stamped onto every toolpath of the operation wherever an export collects them (`GCodeExporter.operationToolpaths`), and `ProgramBuilder` turns it on after the spindle start, off before a tool change, a pause and the footer, and Mist to Air through `M9` (never both). It is left out of the staleness comparison (`withoutPostSettings`), so changing it never recalculates. Merging toolpaths with different coolant is refused. Mist stays offered on GRBL (LoftLine cannot know how a controller was compiled); Help says to use Air on a stock build.
- **park-and-probe — the sequence is written in code, on the machine, from the installed machine.** Spec: `docs/specs/2026-10-27-post-features-design.md` (revision 10, after three review rounds and six verification passes). Settings live on `MachineDefinition.toolChangeProbe` and reach a post only through `applied(to:)` as a never-coded `ProbeSetting`, so no post file or project copy can switch probing on; `ProjectPost.resolve` always takes the probe from the machine installed here (converted to the copy's units), because it describes this shop's hardware today, and refuses a project whose copy probes on a machine that is not set up for it here. Every condition under which no valid program exists throws `PostError.probe`, so there is no Save Anyway. Probing is allowed only with a built-in post compared by value (a post has no dialect field and a machine's post list is editable); a post editor (part 3) can add a declared controller.
- **mach4-zero — Mach4 sets Z through the owner's macro.** Mach4's `G10 L20 Pn` sets the extended offset G54.1 Pn, not "this position is Z", and `G31` neither stops without contact nor sets anything (Mach4 Mill G-code manual, G10 and G31). So the Mach4 sequence calls `M<n> P<plateZ>`, the owner's macro, which stops on no contact and sets the active offset; a fixed recovery line (`G17 G40 G49 G80 G90 G94 G90.1|G91.1 G20|G21 G5x`) follows it, never the editable post preamble. The validator checks the macro's P against the Z helper but cannot see what the macro does: the air-probe procedure (TESTING.md) is the gate.
- **probe-bounds — what bounds a mistake.** Every traverse runs at `topZ` (machine coordinates), the operator jogs Z to about half the probe travel above the plate, and the probe travel is no more than the plate thickness, so a missed contact with the plate in place stops at or above the material top. With no plate at all it can end up to the probe travel (at most 1 in) below the top, spindle off; the placement stop's continuity check guards that. On GRBL `topZ` must be at most −1 mm: GRBL sets the homed position from the pull-off (`$27`) so that machine Z 0 is the switch's trigger point, whatever `$27` is; −1 mm stays 1 mm below it, and the dry run confirms it. Software cannot know where the stock top or a clamp is in machine coordinates, so `topZ` clearing the longest bit over them is a dry-run check.
- **spot-check — against the whole posted sheet, switched off too.** The plate footprint is a disc of the plate's greatest extent (a 32-gon around it) and is checked against the material, keep-out zones, clamps and every operation of the sheet whose job is posted (a single toolpath's own sheet), switched on or off: a pocket cut earlier and switched off is still a pocket under the plate. With probing on, every export calculates the whole sheet first; the missing-from-the-program errors still judge only what is exported. `sheetToolpaths` is optional on `export` and nil with probing refuses, so a forgotten caller fails closed.
- **probe-validator — a state table, independent of the builder where it counts.** `ProbeSequenceChecker` walks needsProbe, lifted, parked, swapReady, swapped, leaving, atSpot, placed, probed, zeroedAtSpot, cleared, ready; a block it does not list keeps the state and gets today's checks. The independent checks are the zero's value (from the validator's own job through the Z helper), the work offset (tracked modally, required at the spot, the zero and every cut), `G53` X/Y only from the traverse height, the stops, no descent at the spot before X/Y leaves it, and cuts and the spindle only once the plate is removed. A sequence deleted together with its `T` word cannot be seen.

## The post editor (2026-10-28)

- **post-editor — a sheet with one synchronous report.** Spec: `docs/specs/2026-10-27-post-editor-design.md` (revision 4, after three review rounds and two verification passes). Toolpaths ▸ Post Processors… is a sheet on the document window (the Settings window is a fixed 640 x 480, and the UI harness can open a sheet). Built-in posts are read-only; Duplicate makes an unsaved draft, which keeps the built-in's controller. `PostDraftReport.make` runs the static rules first and posts a fixed sample job (`PostSampleJob`: two tools, CW and CCW arcs, a pause between toolpaths, a tool change with no pause, Mist) only when they pass, so a typed value never reaches the builder. The validator cannot see a swapped arc code, `G0 F600`, `M4` or a tool name written as G-code words, so the motion and spindle codes are fixed patterns, placeholders are allowed per template, and user text only inside a comment. Stops are checked in the parsed sample program, not the template text: each tool change needs `M0` or `T<that tool>` then `M6` (an optional `M1` does not count), and the pause a parsed `M0`. Any validator issue on the sample blocks Save, except the coordinate shift of exactly `G53 G0 Z0`. Limits, speeds and the RPM range are the post's fallback machine numbers, so the sample fits them rather than test them. Closes the open item in `pause-1`: the pause template is now editable in the form, not only in a saved post's JSON.
- **post-files — a post file is named after its id, and Delete goes to the Trash.** A file whose name is not exactly `<id>.json`, whose id is not a plain file name, or whose id an earlier file already loaded, is listed under Did not load with the reason, as are files that do not decode (part 1's promise). This changes what loads for a misnamed file (renaming it fixes it); projects that carry its copy keep posting with the copy. New posts are created exclusively, so two windows cannot overwrite each other's. Delete moves the file to the Trash through an injected function, so tests never touch the real Trash.
- **post-controller — a custom post can declare its controller.** `PostProfile.controller` (coded only when set; built-ins stay nil and keep part 2's by-value mapping). A post copy in someone else's project that declares a controller can probe on a machine set up here, consistent with part 1's "the copy posts". The schema stays 1: none of parts 1 to 3 has shipped and v0.2.0, which ignores the key, has no probing.
- **probe-g53-written — part 2 fix.** `ProbeSequenceChecker` compared machine-coordinate values within half a digit of the exact value, but the builder writes them rounded toward zero; an inch post at 4 decimals with GRBL's top Z of −1 mm (written `-0.0393`) was refused at export. It now compares with exactly the digits written.

## Sharing a post (2026-10-28)

- **post-share — a post is shared as its JSON, and enters only through the editor.** Spec: `docs/specs/2026-10-28-post-share-design.md` (revision 3, after two review rounds and two verification passes). Export writes a saved custom post's `toJSON()` as `.loftlinepost` (a built-in is on every Mac; importing one would only rename it). Import and Add This Project's Post open an unsaved draft in Post Processors, so every part 3 check runs and only Save writes; Import never takes an id a built-in or a file here has (`importID`), Add keeps the project's id or refuses, so the project then finds its post installed. A file over 1 MB is refused before it is read.
- **carried-raw — the project's post is offered as it carries it.** `carriedPostNotInstalled` returned the post with the machine's limits applied; adding that would have installed the machine's envelope as the post's own limits and shown a false copy-differs warning at once. It returns `ProjectPost.postCopy(of:)` now; its pickers read only the id and the name.
- **empty-pause — one rule on every read path (fix).** A post whose `pause` is `[]` posted no stop at all at a pause, while the same post with `pause` absent stopped. `PostProfile.normalized` reads `[]` as the default pause, and the posts folder, an import and a project's own copy all go through it, so a carried copy with an empty list now posts the default stop and equals the post Add installs. A new save that fails to write removes the file it created.

- **more-posts — three more built-in posts, chosen so none needs a controller feature LoftLine has not proven.** Spec:
  `docs/specs/2026-10-28-more-built-in-posts-design.md` (revision 4, after three review rounds). `generic-grbl-inch` (the GRBL mm
  post in inches, limits and rates rounded down so it never allows more), `linuxcnc-inch` and `linuxcnc-mm` (the Mach dialect with
  M2 and `.ngc`). Existing posts, goldens, samples and built-in machines keep their bytes; the new posts come after them in
  `BuiltInPosts.all`, so defaults and pickers start as before. LinuxCNC stops for a tool with `M5`, a `(MSG, …)` line and `M0`,
  not `T{T} M6`: M6 completes at once on a config that loops `tool-change` back, and a T missing from the tool table aborts. M0
  stops everywhere but cannot re-zero Z (LinuxCNC cannot touch off while paused), the same as the GRBL post's M0; Help says to
  save one file per tool and touch off before each. A single multi-tool file is still allowed for both, with a warning
  (`ToolChangeZ`, added after the final review): a program that changes tools with a post whose tool change neither probes,
  applies a tool length offset nor calls M6 says to save one file per tool. A warning, not a refusal: the GRBL mm post has posted
  such files since it shipped, and a sender may handle the stop. No Mach3 posts: they would write the Avid posts' G-code
  byte for byte. A Mach3 owner can list the Avid posts in a machine of their own, with Mach3's tool change set to stop, `G4 P` in
  seconds and touch-plate tool changes off (the Mach4 probe sequence calls a Mach4 macro); nothing has run on Mach3, so this is
  here and not in Help. Probing: `generic-grbl-inch` probes as GRBL, and `ToolChangeProbe.defaults(for:)` now asks
  `probeController` of every listed built-in, so a machine listing only the inch post starts with GRBL (it got Mach4 and was then
  refused). The LinuxCNC posts have no probe sequence. Mist coolant's M7, which stock GRBL rejects, is out of scope: it already
  applies to the GRBL mm post, the coolant form and Help warn, and the editor report checks LoftLine's rules, not a controller's
  build options. A user post file that already has one of the new ids keeps overriding the built-in, by the existing rule.
- **optional-stop-grbl — an optional stop on a GRBL post writes M0 (#115).** GRBL ignores M1 (`gnea/grbl` `gcode.c`: "Optional
  stop not supported. Ignore.") and has no Optional Stop switch, so the pause a form promised never stopped the machine.
  `PostProfile.honoursOptionalStop` is false for a post that speaks GRBL, by the rule probing already uses
  (`BuiltInPosts.probeController`: a built-in GRBL post unchanged, or a custom post that declares GRBL), and
  `stopCode(for:)` then writes M0. No new post field: a field an older LoftLine drops would post M1 again, which the schema
  rule answers with a version bump that makes older copies refuse every project carrying a GRBL post. A custom GRBL post
  that declares no controller still writes M1; its owner can declare GRBL or put M0 in its pause template. The program
  header lists an M1 as "M1, stops only with Optional Stop on" instead of claiming the machine waits; the job sheet and the
  pause form say what the post writes. LinuxCNC keeps M1 (it has the switch).
- **othermill-post — built-in Othermill posts and machines, with the Bantam Tools software's setup checked at export (#114).**
  Spec: docs/specs/2026-10-28-othermill-post-design.md (revision 4; four reviewers, three rounds). `othermill-inch` and
  `othermill-mm` write only codes the software runs (a line it cannot run is skipped silently): units, `G90 G94 G17 G55`, a
  tool change of `M5`, a comment and `T{n} M6`, a 4 s dwell, helices as lines, `M30`; the machines `othermill-pro` (listed
  first, since a project with no machine takes the first that lists its post) and `othermill`. Dissent: Autodesk's
  `othermill.cps` leaves M6 off by default and refuses a second tool; LoftLine allows several tools because Bantam's
  Troubleshooting page says `M6 T1` prompts for the swap and touches off. That is the weakest fact, and TESTING's owner
  check runs a two-tool file first. The software puts file X0 Y0 Z0 at the stock's front-left top, so `OthermillSetup.issues`
  (PostCore, called beside `ToolChangeZ` in `GCodeExporter.export`) reports as errors a Z zero other than the material top,
  an XY origin other than the lower left, a non-zero datum offset (nil counts as zero, so tiles pass), a move or the move
  home past the X/Y travel measured from that corner, and coolant (one error naming the toolpaths); and warns when the stock
  plus the highest Z any move, Home Z, Safe Z or a raised approach reaches is more than the Z travel, and when the travel,
  feed, rapid or spindle range checked against is bigger than the Othermill's. Errors, not a refusal: they keep Save Anyway
  because the Z-zero convention is the vendor's documented default, not confirmed for imported G-code, and nothing in the
  post processor changes, so the post editor's sample (with Mist) and the golden loops still post every built-in. The posts
  are recognised by id, which a project's copy keeps, so a later edit to the built-in cannot switch the checks off for saved
  projects; a duplicate under a new id loses them (Help says so), and a LoftLine older than this has none. The optional
  stop writes M0 by id too (TinyG treats M1 as M0, so this is a labelling choice), unlike GRBL's by-value rule from #115: an
  edited post that keeps an Othermill id still writes M0. The program header keeps "the machine waits for Cycle Start" (the
  Bantam button is Resume; changing it would move every post's golden bytes for a synonym). `goldenProgramsPassTheValidator`
  checks the Othermill rows on the Avid's limits, since its 12 x 8 in fixture cannot fit the 5.5 x 4.5 in bed, and a separate
  small job checks their own limits. `samples/expected/othermill-*` are regression bytes, not runnable Othermill files: the
  samples are 24 x 12 and 12 x 8 in, posted with their own machine (the Avid).
- **dwell-ms — a post can dwell in milliseconds (#99 item 1).** Spec: docs/specs/2026-10-28-post-engine-options-design.md
  (revision 4; three review rounds). `{SECONDS}` printed `G4 P3` for the spin-up, a 3 ms wait on a controller whose `P` is
  milliseconds (MASSO, NcStudio, UCCNC by default), then a plunge into a bit not up to speed. The dwell template may now use
  `{MILLISECONDS}` (`PostProfile.dwellValues`: whole ms, `%.0f`), and only the dwell template: `{SECONDS}` stays seconds
  everywhere. `PostProfile.dwellProblem` keeps a post from mixing them (a millisecond post may not use `{SECONDS}` in another
  template) or using milliseconds where `P` is seconds (a post declaring GRBL, an Othermill post by id), and bounds the
  spin-up dwell to 0–3600 s; the editor lists it, and the builder refuses to post with it (`PostError.invalidPost`), since a
  post file or a project copy never passes the editor. Every toolpath dwell is bounded to 3600 s too, for every post
  (`PostError.dwellTooLong`; a 4,000 s drill dwell exported before and is now refused): beyond about 1.8e305 s `%.0f` prints
  `INF`. Schema: this supersedes the write rule in `snapshot-schema`. `PostProfile.currentSchemaVersion` (the highest version
  read) is 2; a post is written with `requiredSchemaVersion`, 2 only when its dwell uses `{MILLISECONDS}`, and read back as 1,
  so memory always holds 1 and the version never reaches value equality (`BuiltInPosts.probeController`, which #115's GRBL M0
  rule needs). Builds from `98858e5` on refuse a millisecond post ("made with a newer LoftLine") and still read every other
  post; v0.2.0, the one release, predates `schemaVersion` and would load a millisecond post file from the posts folder and post
  `G4 P{MILLISECONDS}` literally (projects are refused there by the project format version). Gap: the G-code file preview
  still guesses a `G4 P` unit (`P > 100` is ms), right for a millisecond spin-up and wrong for a millisecond dwell of 100 ms
  or less. The rest of #99 (a first-line prelude, CRLF, units words, a forced-dot seconds placeholder) moves to the dialect
  issues that need them, with the readers this review found.
